## 1. 先前已排除的错误方向

### 方向 A：直接用本地主题库做默认推荐

问题：

- 伪推荐
- 和浏览事件库入口没有本质差异
- 容易再次退化成“按 storyScore 排前几条”

最终结论：

- 默认推荐入口不能以本地事件库作为候选来源

### 方向 B：主题阶段只输出一个标题

问题：

- 下游仍要自己猜“这次到底怎么讲”
- 容易重新引发 topic/script 之间的边界漂移

最终结论：

- 主题阶段正式终点是 `Topic Package`，不是标题

### 方向 C：自定义主题继续暴露大量内部 draft 字段

问题：

- 自定义主题会退化成 prompt 编辑器
- 用户实际上在改系统内部对象

最终结论：

- 自定义主题只能做事件识别、candidate 生成与确认
- 不再让用户直接编辑内部 draft 结构

## 2. 主题阶段真正要解决的问题

主题阶段不是“决定写什么标题”，而是解决这几个问题：

1. 这次到底讲哪件事
2. 这次从哪个切口讲
3. 这次讲多大范围
4. 哪些桥段一个都不能缺
5. 哪些地方不允许越界
6. 最终要给 script 一个怎样的正式输入对象

## 3. 三入口的最终分工

### 系统自动推荐

- 默认入口
- 负责发现值得讲的新候选
- 候选来源主要依赖开放发现
- 本地层只负责约束和记忆，不负责供给候选

### 事件库

- 供用户主动指定 event
- 不是 final topic 库
- 用户选中 event 后，系统仍需生成 candidate 再确认

### 自定义主题

- 接收用户灵感性输入
- 先做事件识别与归一化
- 再生成 candidate
- 最终仍然统一收敛到 `Topic Package`

## 4. 为什么引入 Event Registry

原因不是为了把系统重新做成封闭题库，而是为了解决：

- 同一事件不同叫法如何去重
- 如何避免刚讲过的明星题又进推荐
- 如何记录同簇疲劳和人物疲劳
- 如何做命名归一化与混淆控制

最终结论：

- Event Registry 是“身份账本”和“记忆层”
- 不是候选供给层
- 不是人工浏览库

## 5. 为什么 Topic Candidate Card 和 Topic Package 要分开

讨论中已经明确：

- 给用户看的对象不能太重
- 给 script 阶段的对象又必须足够稳

所以必须拆成：

### Topic Candidate Card

- 面向用户决策
- 强调可比较、可理解、可确认

### Topic Package

- 面向系统执行
- 强调范围、冲突、必讲节点、禁写项、史料锚点

## 6. 为什么 family 要从 5 个扩到 8 个

早期曾尝试用 5 个大类：

- 使臣博弈型
- 刺杀政变型
- 战场翻盘型
- 权谋局中局型
- 末路崩塌型

问题：

- 对 `继承夺位 / 变法治术 / 朝堂博弈 / 人物命运` 覆盖不足
- 一些题材会被讲得很别扭

后来结合旧主题库类别分布，扩成 8 个主家族：

- 外交压场型
- 战场翻盘型
- 刺杀政变型
- 朝堂博弈型
- 继承夺位型
- 变法治术型
- 乱局崩盘型
- 人物命运型

并补充：

- 主家族 + 副家族
- 通用安全槽位

## 7. 推荐审核为什么改成轻链路

旧项目早期推荐失败的一个根因是：

- 推荐对象太重
- 审核太晚
- 失败后靠重试修

新结论：

- 推荐阶段的对象必须是结构化 candidate，不是长文案
- 审核链必须是：
  - 本地硬筛
  - 身份/重复筛
  - 单一轻评审
- 失败以淘汰坏候选为主，不以修复坏候选为主

## 8. 为什么要单独做 Candidate Cache

原因：

- 系统推荐可能一次出现多个高质量 candidate
- 如果每次只选一个，其余全部丢掉会浪费

但又不能直接写入事件库，因为：

- candidate 是上下文化对象
- event 是稳定身份对象

最终结论：

- 单独建立 `Recommendation Candidate Cache`
- 用于会话内复用和跨任务短期复用
- 不直接当知识库，不直接当浏览库

## 9. 当前仍未完全收敛的点

- `family_confidence` 的具体计算方法
- Event Registry 匹配阈值
- Candidate Cache 精确生命周期
- 主题阶段轻评审阈值
