# 视频流水线工程经验参考文档

日期：2026-05-09

定位：本文档记录旧项目积累的工程经验，供 asset planning / assets / compose 阶段正式设计时参考。
它不是架构决策文档，也不替代正式设计 implementation plan。
当相关阶段进入正式设计时，应从本文档提取约束，写入该阶段的架构文档与设计文档。

---

## 1. 流水线各产物工程要点

### 1.1 口播文案（已完成）

当前已在 `topic → script` 阶段完成。不在本文档范围内。

---

### 1.2 口播音频（TTS）

**生成方式**

- 调用阿里百炼 CosyVoice 等 TTS API。
- 单次 API 调用有字数/时长上限，较长脚本必须**分段提交**，分批生成多个音频片段，再合并成完整口播音频。

**分段策略**

- 切分点必须在自然语言边界（句末、逗号等），不能在词语中间截断。
- 合并后的衔接点需要保证音调和语气连续，不能出现机械拼接感。
- 建议在 asset planning 阶段就确定切分方案，而不是在 assets 阶段临时截断。

**音色管理**

- 需要创建或指定音色（voice_id），后续所有 TTS 任务复用同一个 voice_id。
- 同一个项目内的所有 TTS 子任务必须使用同一个音色，否则合成后音色会在句间跳变。
- voice_id 应作为 AssetTask（TTS 类型）的显式参数，不能隐式假定。

**最终时长**

- 最终口播音频时长是整个 compose 阶段的时间轴 source-of-truth。
- storyboard 的 `start_hint_sec / end_hint_sec` 只是估算提示，不能用于 compose。
- compose 必须等 TTS 合成完成后，以实际音频时长对齐所有视觉素材。

---

### 1.3 字幕

**生成策略**

- 字幕不是从脚本文本机械切行，而是从 TTS 音频时间戳派生。
- 字幕生成任务依赖 TTS 任务完成，不能并行。
- 字幕切分需要在语义合理的位置断行，不能只按字数截断。
- 每行字幕建议控制在 15-20 字以内，保证屏幕可读性。

**对齐**

- 字幕时间戳应与口播音频逐字/逐词对齐，而不是按段均分。
- 如果 TTS API 返回词级时间戳（word-level timestamps），优先使用。
- 字幕行间隔（呼吸感）必须与口播节奏吻合，不能超前或滞后超过 0.2 秒。

---

### 1.4 分镜图（静态图片素材）

**生成数量**

- 每个 storyboard segment 可能需要 1 张或多张图片：
  - `editing_hint: single` → 1 张
  - `editing_hint: montage` → 通常 3-5 张连切图
  - `editing_hint: cutaway` → 插入场景图 1-2 张 + 主场景图
- 生成张数在 asset planning 阶段确定，不在 storyboard 或 assets 执行阶段决定。

**提示词工程**

- 提示词（prompt）应在 asset planning 阶段基于 storyboard 的 `scene_description`、`visual_elements`、`framing_hint`、`content_type` 自动生成初稿。
- 历史故事场景建议在提示词中加入朝代风格约束（如"汉代宫廷"、"战国战场"）。
- 避免把人物名字直接作为生图提示词主体，容易失控。改用人物特征描述（服饰、动作、表情、场景关系）。

**人物一致性**

- 同一个项目内出现的主要人物，需要在多张图之间保持视觉一致性。
- 策略选项（在 asset planning 设计时择一确认）：
  - 在所有图片任务中共用同一段角色特征描述作为 prompt 后缀
  - 使用支持角色一致性的模型参数（如 ControlNet、角色 seed 固定）
  - 第一张图生成后，后续图用 image-to-image 参考风格
- 当前百炼 API（wanx 系列）的人物一致性能力有限，需要在设计时明确期望值，不能过度承诺。

**用户预览与修改**

- 图片生成后需要支持用户预览。
- 用户不满意时，应支持两种干预方式：
  - 修改/补充提示词，重新生成
  - 提供自然语言修改意见，由系统转化为 prompt 修改后重新生成
- 这个交互节点意味着图片任务不是一次性流水线，需要在 assets 阶段设计"可迭代"的任务状态（生成中 / 待预览 / 已接受 / 重新生成中）。

---

### 1.5 分镜视频

**成本与质量平衡**

- 视频生成成本远高于图片生成。对于不需要动态内容的场景（如文字卡、地图、简单场景），优先考虑以下替代方案：
  - 使用 Remotion 对静态图片做推拉/淡入淡出等简单动效，成本极低
  - 使用图片 + Ken Burns 效果（缓慢缩放移动）代替视频
- 只有以下场景才建议生成真实视频：
  - 有明显动作（战斗、奔跑、人群）
  - `motion_hint` 为 `push_in` / `pull_back` 且静态图无法表达
  - `editing_hint: montage` 且对流畅度要求高

**视频生成约束**

- 单次视频生成时长通常上限为 5-10 秒，超过需拆分。
- 视频时长应与 storyboard segment 的 `end_hint_sec - start_hint_sec` 近似，最终以口播音频时长裁剪对齐。
- 视频与口播音频的时长对齐在 compose 阶段完成，assets 阶段只负责生成"足够长"的原始素材。

**供应商**

- 当前参考供应商：阿里百炼（图片：wanx 系列，视频：CogVideoX 等）。
- 架构上应保留供应商可替换性，AssetTask 中的模型参数应作为可配置项，不硬编码进业务逻辑。

---

### 1.6 合成（Compose）

**时间轴**

- 时间轴的唯一 source-of-truth 是最终合成口播音频的实际时长。
- storyboard 的时间提示只用于大致分段，不用于最终剪辑。
- 每个视觉素材（图片/视频）的展示时长 = 对应口播音频片段的实际时长。

**轨道**

- 最终成片至少包含四条轨道：
  - 视觉轨（图片/视频）
  - 口播音轨
  - 字幕轨
  - 背景音乐轨（可选）

## 2. 可能遇到的问题清单

以下问题来自旧项目经验，供后续各阶段设计时参考并提前设计应对机制。

---

### 🔴 高频 / 高影响问题

**A. 字幕对不上口播**

- **现象**：字幕与音频时间偏移，或切行位置不合理（断在词语中间，或单行字数过多）。
- **根因**：字幕生成没有用 TTS 词级时间戳，或按固定时长均分。
- **应对**：字幕任务必须以 TTS 时间戳为输入；若 API 不返回词级时间戳，使用 forced alignment 工具补齐。

**B. 口播音色不合适 / 语气偏差**

- **现象**：音色太机械，或语气与历史故事风格不匹配（太轻松/太平淡/无起伏）。
- **根因**：未对 TTS 参数做风格调整，或所选音色本身不适合口播叙事风格。
- **应对**：
  - 在 asset planning 设计时，提供可选音色清单，并标注各音色适合的风格（如"男声·沉稳叙事"）。
  - 支持用户在生成前选择或试听音色，避免整批生成后才发现音色不对。
  - 保留重新选择音色 + 重新生成所有 TTS 的回滚路径。

**C. TTS 分段合成不自然**

- **现象**：多段音频合并后，衔接处出现明显的停顿断层或音量突变。
- **根因**：切分点选在了语气未完结的位置，或两段音频的末尾/开头静音时长不一致。
- **应对**：
  - 切分点只能在句末标点（。？！……）或自然停顿处。
  - 合成前对每段音频的末尾做淡出、开头做淡入处理，避免硬拼接。
  - 合成结果应自动做衔接质量检查（短时能量突变检测）。

**D. 视频成本过高**

- **现象**：每条视频大量使用视频生成，导致单条视频生产成本不可接受。
- **根因**：未在 asset planning 阶段做"图片 vs 视频 vs Remotion"的决策，默认全用视频。
- **应对**：在 asset planning 设计时，明确决策规则（参见 1.5 节）；引入成本估算字段，让用户在生成前看到预估费用。

---

### 🟡 中频 / 中影响问题

**E. 人物在不同分镜中外貌不一致**

- **现象**：同一人物在不同图片中服装、面貌差异明显，破坏历史故事的沉浸感。
- **根因**：各图片任务独立生成，没有角色一致性约束。
- **应对**：在 asset planning 层建立角色描述模板，所有涉及该人物的图片任务共用角色特征描述；优先选用支持角色一致性的生成模型。

**F. 生图提示词效果不稳定**

- **现象**：同一提示词多次生成结果差异很大，或某些提示词始终无法生成期望画面。
- **根因**：提示词过于依赖抽象描述，缺乏具体视觉约束；或对生成模型的能力边界理解不足。
- **应对**：建立提示词模板库（按 `content_type` 和 `framing_hint` 分类），避免每次从零写提示词；在 asset planning 阶段对提示词做初步质量检查。

**G. 视觉素材与口播内容不对应**

- **现象**：画面展示的是楚国宫殿，但口播在讲晏子的外貌；或 montage 图片之间没有叙事逻辑。
- **根因**：storyboard 阶段的 `visual_intent` 描述过于抽象，asset planning 生成的提示词与口播内容脱节。
- **应对**：asset planning 的提示词生成必须以 `script_excerpt` 为核心约束，而不是只参考 `scene_description`。

**H. 视频时长与音频时长不匹配**

- **现象**：视频素材比对应的口播片段短或长，导致 compose 时出现画面卡帧或提前跳切。
- **根因**：视频生成时长估算有误，或 compose 未以音频时长为准做裁剪/循环。
- **应对**：视频生成时长应设置 buffer（多生成 1-2 秒），compose 阶段统一以音频时长为准裁剪。

---

### 🟢 低频 / 可接受问题

**I. 背景音乐与故事情绪不匹配**

- **现象**：系统自动配的背景音乐与历史故事的紧张/悲壮/戏谑氛围不符。
- **应对**：第一版背景音乐允许由用户手动指定，不纳入自动生成流水线。

**J. 字幕样式不符合平台要求**

- **现象**：字体、颜色、位置不符合目标平台（抖音/B站）的风格习惯。
- **应对**：字幕样式参数化，在 compose 阶段提供预设模板，允许用户选择。

**K. 音频合成后出现底噪或爆音**

- **现象**：TTS 生成的音频片段在合成后出现底噪或某段音量异常。
- **应对**：合成前对所有音频片段做归一化（normalization）处理，合成后做响度检测。

---

## 3. 各问题与流水线阶段对应

| 问题 | 应对阶段 |
|------|---------|
| A. 字幕对不上 | assets（字幕任务设计）+ compose |
| B. 音色不合适 | asset planning（音色选择节点）|
| C. TTS 衔接不自然 | assets（TTS 切分策略）|
| D. 视频成本过高 | asset planning（图片/视频决策规则）|
| E. 人物不一致 | asset planning（角色特征模板）|
| F. 提示词不稳定 | asset planning（提示词模板库）|
| G. 画面与口播脱节 | asset planning（提示词生成策略）|
| H. 视频与音频时长不匹配 | assets（生成时长 buffer）+ compose |
| I. 背景音乐不匹配 | compose（用户手动选择）|
| J. 字幕样式问题 | compose（样式模板）|
| K. 底噪/爆音 | assets（音频后处理）|

## 4. 供应商参考

| 类型 | 参考供应商 | 备注 |
|------|-----------|------|
| 图片生成 | 阿里百炼 wanx 系列 | 需保留供应商可替换性 |
| 视频生成 | 阿里百炼视频生成 API | 成本高，优先评估是否需要 |
| TTS | 阿里百炼 CosyVoice | 注意音色选择和分段策略 |
| 静态图动效 | Remotion | 低成本替代视频生成 |
| 字幕时间戳对齐 | TTS API 词级时间戳 / 第三方 forced alignment | 视 API 能力决定 |
