# 2026-07-17 Topic 轻审核最小真实验证记录

## 验证范围

- 样本：`harness/samples/topic-script/yanzi-shichu.sample.json`
- Provider / model：当前运行环境配置的 OpenAI-compatible provider / `glm-5.2`
- 范围：仅运行 Topic Builder、轻审核和必要的一次补充，不进入 Script
- 请求上限：4 次 provider 请求
- Builder 内容策略：保持不变，仅使用已落地的 4 候选数量合同

## 结果

- 运行成功，总墙钟耗时 `131.961s`。
- 首轮 Builder 产出 4 条候选。
- 首轮轻审核通过 3 条，淘汰 1 条，首次通过率为 `3/4`。
- 被淘汰项的 `consistency_issue` 为 `overclaim_or_ambiguity`：标题与角度声称“三设/三层”，但候选内容只支撑两轮，计数不成立。
- 流程触发一次补充；跨轮去重后只送审 1 条新增候选，该候选通过。
- 最终返回 4 条合格候选，`zero_eligible_candidate=false`。
- 整个流程在 4 请求硬上限内完成；结合 Builder、首轮轻审核、补充 Builder、补充轻审核四个实际步骤，可确认本轮没有额外 transport retry 或 structured fallback。

最终标题：

1. 狗门之辱：晏子用一句话逼楚王开正门
2. 橘过淮北变枳：一场“水土审判”的反杀
3. 弱使入强廷：晏子在楚王眼皮底下守住国格底线
4. 楚王用狗门压使节等级，晏子一句归谬逼开正门

## 结论与边界

- 轻审核在本样本中成功拦截了一条明确的内部过度断言，并且没有把风险项回填给用户；审核兜底路径有效。
- 首轮只淘汰 1 条仍会触发完整的“补充 Builder + 第二次轻审核”，使本轮达到 4 次 provider 调用；`131.961s` 仍不满足理想交互速度。
- 最终候选中有两个围绕狗门反击的相近角度。该样本是单事件 seed，允许多切口，但这仍是后续观察 Builder 角度差异度的信号，不应由轻审核承担排序或多样性职责。
- 单个样本不足以证明普遍的首次通过率、风险召回或延迟分布，也不足以授权立即修改 Builder Prompt。
- 当前保持 Builder 不变；若继续诊断，应优先增加极少量代表样本并记录各调用耗时/Token，判断主要延迟来自 Builder、轻审核还是补充路径，再决定是否单独设计 Builder 优化或调整补充策略。
