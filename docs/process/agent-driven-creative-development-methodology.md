# Code Agent 驱动创意项目开发方法论

本文总结 `story-video-forge2` 在接近完整视频流水线过程中形成的开发经验，用于指导后续 agent 协作、harness 设计、阶段验收与新项目复用。

本文不是新的 implementation plan，也不授权任何 agent 绕过 `AGENTS.md` 的当前阶段边界。若本文与 `AGENTS.md`、正式架构文档或 harness 规范冲突，以后者为准。

---

## 1. 核心判断

独立开发者使用 code agent 做创意产品时，最大的风险不是 agent 写不出代码，而是 agent 会把不确定性包装成完成度。

本项目的关键经验是：

> 人负责品味、边界与验收；LLM 负责真正需要语义理解的生成；本地代码负责确定性工程；code agent 只能在明确合同内小步实现。

因此，项目治理的重点不是让 agent 更自由，而是让 agent 在每一步都回答清楚：

- 当前阶段消费什么冻结对象。
- 当前阶段产出什么冻结对象。
- 当前阶段不负责什么。
- 哪些判断只能由 LLM 或人工完成。
- 哪些检查可以由本地确定性代码完成。
- 最小验证是什么。

## 2. 本项目踩过的主要坑

### 2.1 用本地规则冒充语义能力

典型表现：

- 用关键词、字符串、黑名单判断“是否爆款”。
- 用本地 validator 判断“内容是否好”。
- 用 fake semantic review 冒充真实审校。
- 无真实 reviewer 时仍返回看似有效的语义结论。

修正原则：

- 本地 validator 只允许做结构、合同、引用、体量、顺序、文件、状态等确定性检查。
- “是否抓人”“是否摘要化”“是否有余震”“是否发布级”属于语义或审美判断，只能交给 LLM reviewer 或人工审稿。
- 无真实 reviewer 时允许 `skipped`，不得伪造 `pass`。
- reviewer 当前只能作为 shadow-only 量尺，不能直接升级成自动门禁或主链路 patch。

### 2.2 把结构通过误当成内容通过

脚本阶段曾暴露出一种高频错觉：字段齐全、beat 覆盖、本地校验通过，但正文仍可能像结构摘要，而不是可口播故事。

有效修正是把质量拆成三层：

- `可用线`：不跑题，覆盖硬合同，本地校验通过，无模板污染。
- `爆款首稿线`：在可用线之上，具备开头留存、场面密度、动作/对话、压力升级和结尾余震。
- `发布线`：还需要事实核查、人工审稿、镜头匹配和最终口播打磨。

agent 不得把局部达标说成整体达标，也不得把“结构通过”说成“发布可用”。

### 2.3 prompt 堆叠导致约束打架

创意质量问题很容易诱导 agent 继续堆 prompt 口号，例如“更爆款”“更抓人”“更有画面感”。这类重复口号会增加模型困惑，并且难以验证。

有效做法是把抽象口号转成短而明确的可执行合同：

- 开头必须绑定具体人物、压力源、选择或代价。
- 核心场面必须有动作、反应、压力或不可逆后果。
- beat 必须推动局面升级，而不是只被点名。
- 结尾必须回收到代价、判断或余震，不喊空泛口号。

每次 prompt 改动都应是低耦合小步，并用真实样本或 targeted smoke 观察结果。

### 2.4 跨阶段污染

创意流水线的另一个风险是后续阶段重新理解故事，或者为了下一阶段方便回改上游。

本项目最终形成的有效边界是：

- `topic` 冻结故事合同。
- `script` 只把冻结合同写成可口播首稿。
- `storyboard` 只把脚本翻译成视听计划。
- `asset planning` 只把视听计划拆成素材任务。
- `assets` 只执行或登记素材。
- `compose` 只形成时间线合同。
- `renderer/export` 只消费时间线和素材产物导出。

每个阶段只回答自己的问题，不把故事理解责任一路拖到最后。

### 2.5 历史计划误导当前执行

archive 和 records 有追溯价值，但不能直接作为当前任务入口。

有效规则：

- 当前任务先读 `AGENTS.md`、`docs/README.md`、正式架构文档和当前 plans。
- `docs/plans/archive/` 只作为历史证据。
- `docs/records/` 只在解释历史决策、排查质量回退或读取工程经验时使用。
- 若要重启历史方向，先写当前日期的 design + implementation plan。

### 2.6 单次 reviewer 反馈被过度服从

LLM reviewer 会波动。一次 `patch_once`、`regen_once` 或 `return_topic` 不应自动触发架构变化或 prompt 重写。

有效规则：

- reviewer 输出先归因：是 writer 表达不足、上游材料不足、审校波动，还是合同冲突。
- `return_topic` 只在 topic 合同本身冲突时成立。
- `patch_once/lift` 当前是量尺和后续设计参考，不是自动 patch 动作。
- 不为了迎合单次 reviewer 牺牲整体稿件质量。

### 2.7 把验收压力全部甩给人工

创意产品确实需要人工品味和最终判断，但这不等于每个功能都靠人工肉眼验收。若 agent 只交付一段口头总结，让开发者自己点页面、查文件、猜状态、读日志，就会把独立开发者拖进低效验收泥潭。

典型表现：

- 功能实现后没有自测入口，只能人工逐步点 UI。
- 没有导出可比对的 JSON、截图、trace、report 或样片。
- 前端只读 diff，不跑真实页面。
- 长链路只说“已接上”，没有提供可复跑命令和输出目录。
- 另一个 agent 无法仅凭交付物复核实现者的声明。

修正原则：

- 每个重要功能都应设计自测入口，优先让 agent 自己跑、自己定位、自己修复。
- 每次交付都应包含方便验收的产物：报告、截图、日志摘要、输出目录、测试命令、关键 artifact 路径。
- 前端功能就位后，必须进入真实页面或等价浏览器环境做多轮运行测试，不能只靠代码阅读。
- 人工验收应集中在审美、业务判断和发布取舍，而不是替 agent 做基础状态检查。

### 2.8 上游未稳就启动下游

流水线项目最容易出现的战略性浪费，是上一级还不能稳定输出合格交付物，就开始设计和编码下一层。这样会导致下游被迫替上游补锅，问题定位变混乱，返工量成倍增加。

典型表现：

- `topic` 还没冻结，就开始调 `script`。
- `script` 首稿还不合格，就开始设计 `storyboard`。
- `storyboard` 分镜不稳定，就让 `asset planning` 猜素材任务。
- `assets` 产物不完整，就让 `compose` 兜底时间线。
- `compose` timeline 还不可靠，就急着做最终导出和发布流。

修正原则：

- 每一级都要有明确的合格交付物和冻结标准。
- 上一级最小验证未通过，不进入下一级详细设计和编码。
- 下游只能消费上游冻结对象，不得重新解释上游语义。
- 下游发现问题时，先定位是上游交付物不合格、接口合同缺失，还是本阶段实现错误。
- 宁可晚一点进入下一层，也不要在不稳定地基上扩张功能面。

### 2.9 没有 harness 就开始编码

本项目早期的一个重要正确决策，是在正式业务编码前先建立轻量 harness v1：根目录入口、harness 目录、prompt registry、runtime harness、输出目录、检查脚本与完成/评审规则。这不是“还没写业务先写杂活”，而是先给 agent 协作铺轨道。

如果没有这层 harness，后续很容易出现：

- 新 agent 进入项目后各自挑文档读，理解不一致。
- prompt 散落在代码、notes 或临时文档里。
- 中文 prompt、中文提交、阶段闸门等硬要求停留在聊天记录里。
- runtime 链路只有口头说法，没有可复跑样例和输出目录。
- 检查入口、样本、trace、diagnostics、验收报告各写各的。
- 项目越做越大后，才发现无法稳定复验最早的核心链路。

修正原则：

- 重要流水线项目应在业务编码前先建立最小 harness。
- harness 不重新定义产品对象，只定义 agent 如何执行、检查、记录和复验。
- runtime harness 应尽早成为 P0，而不是后期补测试。
- prompt registry、样本集、输出目录、显式 live check 和验收报告应从第一阶段就有稳定位置。

## 3. 通用开发方法

### 3.1 流水线按闸门逐级推进

流水线项目必须坚持“一级一级来”。每一级都应先形成可验收、可复跑、可冻结的交付物，再开启下一层的详细设计和编码。

推荐闸门：

- 设计闸门：本阶段职责、输入、输出、不负责事项已经写清。
- 合同闸门：主输出对象 schema、字段语义、状态边界已经稳定。
- 生成闸门：本阶段能用真实或代表性样本产出交付物。
- 校验闸门：本地结构校验、runtime smoke 和必要人工观察通过。
- 冻结闸门：文档、测试、records 或验收报告已经吸收当前事实。
- 交接闸门：下游只需读本阶段主合同对象即可开始设计。

一旦闸门未过，下一步不是扩大范围，而是回到最近的失败层修复。不要让下游用兼容逻辑、兜底字段或人工猜测来消化上游不稳定。

### 3.2 先定阶段，不先写功能

每个阶段进入实现前，必须先明确：

- 输入对象。
- 输出对象。
- 本阶段职责。
- 本阶段禁止事项。
- 本地 validator 边界。
- LLM 或人工判断边界。
- 持久化与状态更新规则。
- 最小验证命令或验收方式。

没有这些定义时，不应让 agent 直接实现。

### 3.3 每阶段只产出一个主合同对象

主合同对象是后续阶段的唯一正式入口。

这样做的收益：

- 防止后续 agent 到处读取 prompt、notes、records 重新解释业务。
- 降低阶段间耦合。
- 便于持久化、回归和 diff。
- 便于人工审查“到底变了什么”。

### 3.4 把语义层和工程层分开

语义层适合：

- 选题发现。
- 故事理解。
- 文案表达。
- 分镜视觉化。
- 审稿判断。

工程层适合：

- schema。
- validator。
- persistence。
- API。
- trace。
- diagnostics。
- 文件存储。
- provider job 记录。
- deterministic fake/local fixtures。
- smoke tests。

本地工程层不得越权扮演语义裁判。

### 3.5 用 harness 保护阶段，而不是替代产品判断

harness 的职责是让链路可运行、可复验、可定位，不是证明内容已经发布级。

推荐 harness 分层：

- 单元测试：验证 schema、纯函数、状态转换。
- runtime smoke：验证最小链路可运行。
- five-round 或 sample set：观察真实样本分布。
- explicit live check：验证真实 provider 或真实模型行为。
- acceptance report：输出可被人工或另一个 agent 快速审查的验收报告。
- 人工记录：补足审美、语义、发布质量判断。

真实 live check 不应默认进入自动化门，除非成本、稳定性和失败语义都已设计清楚。

### 3.6 优先建立自测-自修复闭环

面向 agent 的项目不应只追求“能实现”，还应追求“能让 agent 自己验证并修复”。一个成熟功能至少应回答：

- 如何一键构造最小输入。
- 如何运行最小链路。
- 如何输出结构化结果。
- 如何定位失败发生在哪一层。
- 如何区分测试 fixture、fake provider、真实 provider 和人工输入。
- 如何让另一个 agent 根据产物复核。

推荐闭环：

1. 先写最小自测入口，明确输入、输出和失败码。
2. agent 实现功能后先跑自测。
3. 自测失败时，agent 读取输出、定位原因并小步修复。
4. 修复后复跑同一命令，直到得到稳定证据。
5. 最终交付时附上命令、输出路径、关键结果和未覆盖项。

自测不等于自动证明产品质量。它的价值是把基础正确性、链路可运行性和回归风险从人工验收中剥离出去。

### 3.7 交付物要服务验收，而不只是服务实现

每个重要任务都应要求 agent 产出“可验收交付物”。这些交付物不是额外装饰，而是降低人工验收成本的核心工程资产。

推荐交付物：

- 结构化 JSON：展示输入、输出、状态、错误、warnings。
- Markdown report：总结样本、通过项、失败项、人工需关注项。
- 截图或短视频：用于前端、视觉、成片、排版验收。
- artifact manifest：列出生成文件、路径、hash、duration、provider、source。
- trace/diagnostics：记录阶段、耗时、provider 模式、重试、fallback。
- replay command：允许复跑同一验收。
- acceptance checklist：逐项映射用户原始要求。

好的交付物应让另一个 agent 或未来的自己能在不重跑全部链路的情况下，快速判断“实现者到底验证了什么、没验证什么”。

### 3.8 前端必须真实运行，多轮验收

前端问题天然依赖真实交互、布局、加载状态、错误状态和浏览器环境。只读 diff 无法替代体验验收。

前端功能完成后，至少应考虑：

- 启动真实 dev server 或等价预览环境。
- 用浏览器自动化或 computer use 打开真实页面。
- 覆盖空状态、加载中、成功、失败、刷新、深链、重复操作。
- 截图保存关键状态。
- 检查按钮、表单、下载、上传、预览、错误提示和导航是否真实可用。
- 多轮运行，避免只验证一次 happy path。
- 若页面涉及长耗时任务，检查进度语义和恢复行为。

前端验收报告应包含页面 URL、测试路径、截图路径、失败项和未验证项。若无法启动浏览器或服务，必须标注 `未验证`，不能默认为通过。

### 3.9 善用第二 agent 做审查和验收

实现者 agent 很容易对自己的改动过度乐观。复杂任务完成后，可以把交付物交给另一个 agent 做只读审查或验收。

第二 agent 的输入应尽量是原始材料：

- 用户原始要求。
- 当前 diff。
- 自测命令与输出。
- report、截图、artifact manifest。
- 需要验收的页面或接口。

不要把实现者的结论当作事实传给审查 agent。审查 agent 应重新提取验收清单，并逐项标注 `已修 / 部分修 / 未修 / 未验证`。

### 3.10 失败先定位层级，再动手修复

流水线后段暴露的问题，不一定属于后段。比如 render 结果差，可能是素材缺失、compose 时间线错误、asset plan 没有生产合同、storyboard 分镜不清，甚至 script 首稿本身不适合视觉化。

修复前先定位：

- 输入对象是否合格。
- 上游主合同是否表达了本阶段所需信息。
- 当前阶段是否误读了合同。
- 本地 validator 是否漏掉了结构问题。
- 是否需要回到上一级修合同，而不是在本级堆兜底。

原则是：在哪一层引入的问题，就在哪一层修。不要让下游长期背负上游债务。

### 3.11 先做窄切片，再扩能力面

agent 很容易把一个阶段一次性扩成完整平台。更稳的方式是先做一个窄切片：

- 一个代表性样本。
- 一个最小主合同对象。
- 一个 fake/local provider。
- 一个持久化记录。
- 一个最小 API。
- 一个 smoke。
- 一个验收报告。

窄切片跑通后，再扩展 provider、并发、UI、人工介入、发布流和运营能力。这样每次扩展都有稳定基线，不会在大范围半成品里迷路。

### 3.12 建立冻结样本池和回归样本池

创意流水线不能只靠随机样本判断质量。每个关键阶段都应保留少量代表性样本，用于观察回归和边界行为。

样本池应覆盖：

- happy path。
- 上游材料稀薄。
- 高风险题材或复杂结构。
- 长耗时任务。
- provider 失败或跳过。
- 人工介入路径。

这些样本不一定都进入默认自动化门，但应能被显式复跑，并输出可比较报告。没有样本池，agent 很容易修好一个 case、弄坏三个 case。

### 3.13 明确状态失效和重跑规则

流水线项目必须回答：上游变了，下游产物是否还有效。

建议每个阶段设计时都写清：

- 哪些上游字段变化会让本阶段 active record 失效。
- 旧记录是保留为历史，还是删除。
- UI 应回到哪个状态。
- 是否允许复用旧 artifact。
- 哪些 provider job 不应自动重跑。
- 用户手动上传或人工接受的产物如何处理。

没有状态失效规则，项目会逐渐出现“页面显示的是旧产物、后端消费的是新合同、用户不知道哪个是真的”的隐性错乱。

### 3.14 每次任务都写清“不改什么”

agent 特别容易顺手扩范围。每次开始前应输出：

- `任务`
- `目标`
- `本次改动文件`
- `不改什么`
- `验证方式`

结束时应输出：

- `实际改动`
- `验证结果`
- `自审结论`
- `剩余风险`
- `下一步建议`

这不是形式主义，而是防止 agent 把“顺手”伪装成“推进”。

### 3.15 用设计文档吸收经验，用 records 保留证据

建议区分四类文档：

- `AGENTS.md`：当前 agent 工作契约和阶段边界。
- `docs/architecture/`：当前正式架构真相源。
- `docs/plans/`：当前可执行或待收口计划。
- `docs/records/`：历史运行、质量恢复和工程经验记录。

如果某条历史经验仍然有效，应吸收到正式架构或 process 文档；不要要求每个新 agent 反复读旧 records 才能避坑。

### 3.16 编码前先建立最小 harness

对 agent 驱动的创意流水线项目，最小 harness 应该先于大规模业务编码出现。它的作用不是替代产品设计，而是把“怎么做才算受控”提前固化。

建议最小组成：

- 根入口：`AGENTS.md`，说明当前阶段、阅读顺序、硬约束和禁止事项。
- harness 入口：`harness/README.md`，说明检查入口、runtime 命令、输出位置和边界。
- 执行规则：definition of done、review checklist、regression checklist。
- Prompt Registry：正式 prompt 的物理目录、元数据、语言和去重规则。
- 样本集：固定 smoke 样本、扩展巡检样本、reviewer fixture。
- runtime harness：能跑通当前最小链路，并输出 trace、diagnostics 和 artifact。
- 轻量检查脚本：prompt 语言、重复 prompt、schema-doc drift、快速检查。
- 输出目录：统一存放运行产物，默认 gitignored。

这套 harness 不需要一开始很大，但必须让后续 agent 能回答：从哪里开始读、跑什么命令、看哪些产物、什么不能做、失败时怎么定位。

### 3.17 harness 要分清默认门和显式巡检

harness 不能把所有真实调用都塞进默认自动化门。真实 LLM、真实 provider、成片导出、UI walkthrough 往往成本高、耗时长、波动大，更适合显式触发和记录。

推荐分层：

- 默认自动化门：快、稳定、低成本，验证 schema、纯函数、fake/local 链路和固定 smoke。
- 显式真实巡检：真实模型、真实 TTS、真实图像/视频 provider、五轮质量检查。
- 人工/二次 agent 验收：审美、语义、发布判断、复杂 UI 体验。
- 报告读取入口：不重跑昂贵任务，只读取最近一次 summary/report 进行复核。

这种分层能避免两个极端：一是完全不验真实链路，二是把昂贵不稳定的 live check 变成日常阻塞。

### 3.18 harness 输出要可审计、可复盘、可复跑

runtime harness 的价值不只是“跑了一次 pass”，而是留下足够证据，让未来的自己或另一个 agent 能复盘。

推荐输出：

- `summary.json`：总览、通过/失败、关键路径。
- `runtime-diagnostics.json`：阶段、provider、fallback、warnings、耗时。
- `graph-trace-summary.json` 或等价 trace：节点执行和状态流转。
- `llm-interactions/*.md`：prompt、输入、响应、repair context。
- 阶段主产物 JSON：如 script、storyboard、asset plan、manifest、timeline。
- `review.md` 或 `manual-review-checklist.md`：人工和二次 agent 的审查入口。
- screenshots / trace.zip / console-summary / network-summary：前端验收证据。

输出目录应稳定、可指定、可 resume；运行产物默认不进 git，但关键结论应沉淀到 records、plans 或正式文档。

### 3.19 harness 不应反客为主

harness 是执行治理层，不是产品真相源。它应约束 agent 如何工作，而不是重新定义系统是什么。

边界：

- 产品对象、schema、API、阶段职责仍归 `docs/architecture/`、`docs/data/`、正式 plans 管。
- harness 只管理 prompt 资产、运行样本、检查脚本、验收入口和执行规则。
- 如果 harness 和正式架构冲突，先判断是哪一层越权，而不是让检查脚本强行覆盖产品设计。
- 不要把旧项目 harness 直接复制到新项目；只吸收结构和工作流，业务语义必须重新贴合当前项目。

## 4. Agent 反糊弄清单

当 agent 声称“已完成”时，优先检查：

- 是否把本地结构校验说成了语义质量通过。
- 是否用 fake/stub 结果冒充真实 provider 或真实 reviewer。
- 是否把 reviewer shadow 输出升级成主链路动作。
- 是否把局部任务通过说成整体功能通过。
- 是否跳过用户原始验收清单，只复述提交说明。
- 是否为了修一个问题顺手改了上游冻结对象。
- 是否修改 prompt 后没有跑最小回归。
- 是否新增了跨阶段对象但没有 design + implementation plan。
- 是否把历史 archive 计划当作当前计划继续执行。
- 是否声称“发布级”，但没有人工审稿、事实核查和真实页面/成片验收证据。
- 是否让用户人工点页面替代 agent 自测。
- 是否没有提供复跑命令、输出路径或验收 artifact。
- 是否前端改动没有真实浏览器运行记录。
- 是否只验证 happy path，没有覆盖失败、刷新、重复操作或长耗时状态。
- 是否把实现者 agent 的总结当作验收证据，而没有独立复核。
- 是否上一级交付物未合格，就开始下一层详细设计或编码。
- 是否让下游用兜底逻辑长期消化上游合同缺陷。
- 是否只修当前暴露的单个样本，没有回跑冻结样本池或代表性样本。
- 是否上游变更后没有处理 downstream active record 失效。
- 是否没有 harness 入口、固定样本、运行输出和检查命令，就开始大规模业务编码。
- 是否把真实 live check 混进默认自动化门，导致日常验证昂贵且不稳定。
- 是否 runtime harness 跑完后没有留下 summary、trace、diagnostics 或 review artifact。
- 是否让 harness 重新定义产品对象，越过正式架构文档。

## 5. Skill 还是项目文档

### 结论

这套经验应优先放在每个项目的文档体系中，作为 harness 架构和 agent 工作契约的一部分；暂时不应直接抽成一个强约束 skill。

更合适的路径是：

1. 先作为项目 process 文档沉淀。
2. 在 `AGENTS.md` 中保留当前阶段的硬边界。
3. 在 harness 文档中保留项目特定验证入口。
4. 等这套方法在多个创意项目中重复验证后，再抽成轻量 skill。

### 为什么不先做成 skill

skill 的优势是跨项目复用，但它不适合承载太多项目特定事实。

本项目里的大量规则依赖具体上下文：

- `TopicPackage`、`ScriptDraftPackage` 等阶段对象。
- semantic reviewer shadow-only 的当前状态。
- prompt registry 的目录约束。
- video pipeline 的阶段完成度。
- 当前可实施与不可实施边界。

如果把这些直接写进 skill，后续在别的项目中会变成过期上下文，甚至误导 agent。

### 什么内容适合未来抽成 skill

未来可以抽成 skill 的不是本项目事实，而是通用流程：

- 如何为创意 AI 项目划分阶段。
- 如何区分本地确定性 validator 与 LLM/人工语义判断。
- 如何设计主合同对象。
- 如何设计 harness 分层。
- 如何设计自测-自修复闭环与可验收交付物。
- 如何设计流水线级联闸门、冻结样本池和状态失效规则。
- 如何在业务编码前建立最小 harness、Prompt Registry、runtime 输出和显式巡检体系。
- 如何写反糊弄验收清单。
- 如何从 records 中吸收经验而不续跑旧计划。

这个 skill 应保持轻量，只提供工作流和检查清单；项目事实仍留在各项目自己的 `AGENTS.md`、architecture、plans 和 harness 文档中。

建议名称可以是：

- `agent-driven-creative-pipeline`
- `creative-ai-project-governance`
- `harness-first-agent-development`

### 推荐落地方式

短期：

- 本文作为项目 process 文档。
- 新任务仍以 `AGENTS.md` 为最高优先项目契约。
- 涉及重要质量优化时，继续先写中文 design + implementation plan。

中期：

- 把本文中稳定的通用规则提炼成一个简短模板。
- 在新项目初始化时复制为 `docs/process/agent-driven-creative-development-methodology.md`。
- 让每个项目按自身对象和阶段重写示例。

长期：

- 如果至少两个以上项目验证了这套方法，再创建个人 skill。
- skill 只描述通用流程，不内置 `story-video-forge2` 的具体对象与状态。
- skill 触发后要求 agent 先读项目本地 `AGENTS.md` 和 harness 文档，再应用通用方法。

## 7. 当前项目适用建议

`story-video-forge2` 当前已具备较强的阶段治理基础。后续推进前端预览、发布流和人工审稿流时，建议继续沿用本方法：

- 不回改已冻结的 `topic + script`，除非定位到阻塞或回归。
- 继续把 `harness/README.md` 和 runtime harness 作为新 agent 的 P0 入口，不要只依赖口头交接。
- 新增前端、发布、人工审稿能力时，应同步补对应 smoke/live-check/report 入口，而不是功能完成后再补。
- 扩展真实 provider 或成片验收时，应明确默认测试、显式 live check 和人工验收三层边界。
- 任一 downstream 新能力启动前，先确认上一层 active 交付物已经合格、可复跑、可冻结。
- 如果 render/export 或发布流暴露质量问题，先回看 `ComposeTimeline`、`AssetManifest`、`AssetPlan`、`StoryboardPlan` 和 `ScriptDraftPackage`，不要默认在最后一层补锅。
- 前端体验问题必须回到真实页面或等价浏览器验证。
- 发布流和人工审稿流必须先有正式 design + implementation plan。
- 人工审稿流不能被本地评分器替代。
- render/export 的验收要区分 backend job 成功、文件可下载、预览可播放、成片发布可用四个层级。
- 前端预览、发布流和人工审稿流应优先补自测入口与验收报告，减少人工反复点页面的成本。
- 对成片相关链路，交付物应至少包含 render job、输出文件路径、截图或样片、manifest 和失败诊断。
- 对前端工作流，建议保留多轮真实浏览器 walkthrough 记录，让后续 agent 能直接复核体验状态。
- 保留代表性样本池，用同一批样本观察 topic -> render/export 的跨阶段回归，而不是每次只看一个新样本。

这套方法的目标不是降低创意标准，而是保护创意标准不被“看似完成”的工程输出稀释。
