# Code Agent 驱动创意项目开发方法论

本文总结 `story-video-forge2` 在接近完整视频流水线过程中形成的开发经验，用于指导后续 agent 协作、harness 设计、阶段验收与新项目复用。

本文不是新的 implementation plan，也不授权任何 agent 绕过 `AGENTS.md` 的当前阶段边界。若本文与 `AGENTS.md`、正式架构文档或 harness 规范冲突，以后者为准。

---

## 1. 核心判断

独立开发者使用 code agent 做创意产品时，最大的风险不是 agent 写不出代码，而是 agent 会把不确定性包装成完成度。

本项目的关键经验是：

> 人负责品味、边界与验收；LLM 负责真正需要语义理解的生成；本地代码负责确定性工程；code agent 只能在明确合同内小步实现。

因此，项目治理的重点不是让 agent 更自由，而是让 agent 在每一步都回答清楚：

- 当前阶段消费什么冻结对象。
- 当前阶段产出什么冻结对象。
- 当前阶段不负责什么。
- 哪些判断只能由 LLM 或人工完成。
- 哪些检查可以由本地确定性代码完成。
- 最小验证是什么。

## 2. 本项目踩过的主要坑

### 2.1 用本地规则冒充语义能力

典型表现：

- 用关键词、字符串、黑名单判断“是否爆款”。
- 用本地 validator 判断“内容是否好”。
- 用 fake semantic review 冒充真实审校。
- 无真实 reviewer 时仍返回看似有效的语义结论。

修正原则：

- 本地 validator 只允许做结构、合同、引用、体量、顺序、文件、状态等确定性检查。
- “是否抓人”“是否摘要化”“是否有余震”“是否发布级”属于语义或审美判断，只能交给 LLM reviewer 或人工审稿。
- 无真实 reviewer 时允许 `skipped`，不得伪造 `pass`。
- reviewer 当前只能作为 shadow-only 量尺，不能直接升级成自动门禁或主链路 patch。

### 2.2 把结构通过误当成内容通过

脚本阶段曾暴露出一种高频错觉：字段齐全、beat 覆盖、本地校验通过，但正文仍可能像结构摘要，而不是可口播故事。

有效修正是把质量拆成三层：

- `可用线`：不跑题，覆盖硬合同，本地校验通过，无模板污染。
- `爆款首稿线`：在可用线之上，具备开头留存、场面密度、动作/对话、压力升级和结尾余震。
- `发布线`：还需要事实核查、人工审稿、镜头匹配和最终口播打磨。

agent 不得把局部达标说成整体达标，也不得把“结构通过”说成“发布可用”。

### 2.3 prompt 堆叠导致约束打架

创意质量问题很容易诱导 agent 继续堆 prompt 口号，例如“更爆款”“更抓人”“更有画面感”。这类重复口号会增加模型困惑，并且难以验证。

有效做法是把抽象口号转成短而明确的可执行合同：

- 开头必须绑定具体人物、压力源、选择或代价。
- 核心场面必须有动作、反应、压力或不可逆后果。
- beat 必须推动局面升级，而不是只被点名。
- 结尾必须回收到代价、判断或余震，不喊空泛口号。

每次 prompt 改动都应是低耦合小步，并用真实样本或 targeted smoke 观察结果。

### 2.4 跨阶段污染

创意流水线的另一个风险是后续阶段重新理解故事，或者为了下一阶段方便回改上游。

本项目最终形成的有效边界是：

- `topic` 冻结故事合同。
- `script` 只把冻结合同写成可口播首稿。
- `storyboard` 只把脚本翻译成视听计划。
- `asset planning` 只把视听计划拆成素材任务。
- `assets` 只执行或登记素材。
- `compose` 只形成时间线合同。
- `renderer/export` 只消费时间线和素材产物导出。

每个阶段只回答自己的问题，不把故事理解责任一路拖到最后。

### 2.5 历史计划误导当前执行

archive 和 records 有追溯价值，但不能直接作为当前任务入口。

有效规则：

- 当前任务先读 `AGENTS.md`、`docs/README.md`、正式架构文档和当前 plans。
- `docs/plans/archive/` 只作为历史证据。
- `docs/records/` 只在解释历史决策、排查质量回退或读取工程经验时使用。
- 若要重启历史方向，先写当前日期的 design + implementation plan。

### 2.6 单次 reviewer 反馈被过度服从

LLM reviewer 会波动。一次 `patch_once`、`regen_once` 或 `return_topic` 不应自动触发架构变化或 prompt 重写。

有效规则：

- reviewer 输出先归因：是 writer 表达不足、上游材料不足、审校波动，还是合同冲突。
- `return_topic` 只在 topic 合同本身冲突时成立。
- `patch_once/lift` 当前是量尺和后续设计参考，不是自动 patch 动作。
- 不为了迎合单次 reviewer 牺牲整体稿件质量。

## 3. 通用开发方法

### 3.1 先定阶段，不先写功能

每个阶段进入实现前，必须先明确：

- 输入对象。
- 输出对象。
- 本阶段职责。
- 本阶段禁止事项。
- 本地 validator 边界。
- LLM 或人工判断边界。
- 持久化与状态更新规则。
- 最小验证命令或验收方式。

没有这些定义时，不应让 agent 直接实现。

### 3.2 每阶段只产出一个主合同对象

主合同对象是后续阶段的唯一正式入口。

这样做的收益：

- 防止后续 agent 到处读取 prompt、notes、records 重新解释业务。
- 降低阶段间耦合。
- 便于持久化、回归和 diff。
- 便于人工审查“到底变了什么”。

### 3.3 把语义层和工程层分开

语义层适合：

- 选题发现。
- 故事理解。
- 文案表达。
- 分镜视觉化。
- 审稿判断。

工程层适合：

- schema。
- validator。
- persistence。
- API。
- trace。
- diagnostics。
- 文件存储。
- provider job 记录。
- deterministic fake/local fixtures。
- smoke tests。

本地工程层不得越权扮演语义裁判。

### 3.4 用 harness 保护阶段，而不是替代产品判断

harness 的职责是让链路可运行、可复验、可定位，不是证明内容已经发布级。

推荐 harness 分层：

- 单元测试：验证 schema、纯函数、状态转换。
- runtime smoke：验证最小链路可运行。
- five-round 或 sample set：观察真实样本分布。
- explicit live check：验证真实 provider 或真实模型行为。
- 人工记录：补足审美、语义、发布质量判断。

真实 live check 不应默认进入自动化门，除非成本、稳定性和失败语义都已设计清楚。

### 3.5 每次任务都写清“不改什么”

agent 特别容易顺手扩范围。每次开始前应输出：

- `任务`
- `目标`
- `本次改动文件`
- `不改什么`
- `验证方式`

结束时应输出：

- `实际改动`
- `验证结果`
- `自审结论`
- `剩余风险`
- `下一步建议`

这不是形式主义，而是防止 agent 把“顺手”伪装成“推进”。

### 3.6 用设计文档吸收经验，用 records 保留证据

建议区分四类文档：

- `AGENTS.md`：当前 agent 工作契约和阶段边界。
- `docs/architecture/`：当前正式架构真相源。
- `docs/plans/`：当前可执行或待收口计划。
- `docs/records/`：历史运行、质量恢复和工程经验记录。

如果某条历史经验仍然有效，应吸收到正式架构或 process 文档；不要要求每个新 agent 反复读旧 records 才能避坑。

## 4. Agent 反糊弄清单

当 agent 声称“已完成”时，优先检查：

- 是否把本地结构校验说成了语义质量通过。
- 是否用 fake/stub 结果冒充真实 provider 或真实 reviewer。
- 是否把 reviewer shadow 输出升级成主链路动作。
- 是否把局部任务通过说成整体功能通过。
- 是否跳过用户原始验收清单，只复述提交说明。
- 是否为了修一个问题顺手改了上游冻结对象。
- 是否修改 prompt 后没有跑最小回归。
- 是否新增了跨阶段对象但没有 design + implementation plan。
- 是否把历史 archive 计划当作当前计划继续执行。
- 是否声称“发布级”，但没有人工审稿、事实核查和真实页面/成片验收证据。

## 5. Skill 还是项目文档

### 结论

这套经验应优先放在每个项目的文档体系中，作为 harness 架构和 agent 工作契约的一部分；暂时不应直接抽成一个强约束 skill。

更合适的路径是：

1. 先作为项目 process 文档沉淀。
2. 在 `AGENTS.md` 中保留当前阶段的硬边界。
3. 在 harness 文档中保留项目特定验证入口。
4. 等这套方法在多个创意项目中重复验证后，再抽成轻量 skill。

### 为什么不先做成 skill

skill 的优势是跨项目复用，但它不适合承载太多项目特定事实。

本项目里的大量规则依赖具体上下文：

- `TopicPackage`、`ScriptDraftPackage` 等阶段对象。
- semantic reviewer shadow-only 的当前状态。
- prompt registry 的目录约束。
- video pipeline 的阶段完成度。
- 当前可实施与不可实施边界。

如果把这些直接写进 skill，后续在别的项目中会变成过期上下文，甚至误导 agent。

### 什么内容适合未来抽成 skill

未来可以抽成 skill 的不是本项目事实，而是通用流程：

- 如何为创意 AI 项目划分阶段。
- 如何区分本地确定性 validator 与 LLM/人工语义判断。
- 如何设计主合同对象。
- 如何设计 harness 分层。
- 如何写反糊弄验收清单。
- 如何从 records 中吸收经验而不续跑旧计划。

这个 skill 应保持轻量，只提供工作流和检查清单；项目事实仍留在各项目自己的 `AGENTS.md`、architecture、plans 和 harness 文档中。

建议名称可以是：

- `agent-driven-creative-pipeline`
- `creative-ai-project-governance`
- `harness-first-agent-development`

### 推荐落地方式

短期：

- 本文作为项目 process 文档。
- 新任务仍以 `AGENTS.md` 为最高优先项目契约。
- 涉及重要质量优化时，继续先写中文 design + implementation plan。

中期：

- 把本文中稳定的通用规则提炼成一个简短模板。
- 在新项目初始化时复制为 `docs/process/agent-driven-creative-development-methodology.md`。
- 让每个项目按自身对象和阶段重写示例。

长期：

- 如果至少两个以上项目验证了这套方法，再创建个人 skill。
- skill 只描述通用流程，不内置 `story-video-forge2` 的具体对象与状态。
- skill 触发后要求 agent 先读项目本地 `AGENTS.md` 和 harness 文档，再应用通用方法。

## 6. 可复用执行模板

每个新阶段启动前，先写：

```text
阶段名称：
本阶段目标：
正式输入对象：
正式输出对象：
不负责：
本地 validator 只检查：
LLM/人工才可判断：
状态与持久化：
最小验证：
完成后是否冻结：
```

每次验收时，先写：

```text
用户原始验收清单：
1. ...

逐项结果：
1. 已修 / 部分修 / 未修 / 未验证
   证据：

实现者声称完成的范围：

本次实际验证的范围：

不能宣称完成的范围：
```

每次发现 agent 试图“聪明绕过”时，先问：

```text
这个判断是否需要语义理解？
如果需要，当前是 LLM、人工，还是本地规则在做？
如果是本地规则，它是否只在做结构性下限？
如果是 fake/stub，它是否被明确标注为 fake/stub？
如果验证无法覆盖，最终结论是否标成未验证？
```

## 7. 当前项目适用建议

`story-video-forge2` 当前已具备较强的阶段治理基础。后续推进前端预览、发布流和人工审稿流时，建议继续沿用本方法：

- 不回改已冻结的 `topic + script`，除非定位到阻塞或回归。
- 前端体验问题必须回到真实页面或等价浏览器验证。
- 发布流和人工审稿流必须先有正式 design + implementation plan。
- 人工审稿流不能被本地评分器替代。
- render/export 的验收要区分 backend job 成功、文件可下载、预览可播放、成片发布可用四个层级。

这套方法的目标不是降低创意标准，而是保护创意标准不被“看似完成”的工程输出稀释。
