# 2026-04-28 开放发现式 Topic 推荐设计

## 1. 背景

当前 `Topic` 页面已经具备：

- `系统自动推荐 / 事件库 / 自定义主题` 三入口 UI
- `topic -> script` 的主链路
- 运行级 trace 与 LLM 交互日志

但 `系统自动推荐` 仍存在一个关键语义空洞：

- 它之前通过前端硬编码 seed 驱动推荐
- 修复硬编码后，已经不再固定到同一个事件
- 但“系统自动推荐究竟是什么”还没有被正式设计收敛

这会导致后续实现容易在两条路线之间来回摇摆：

1. 让 LLM 直接按条件开放生成候选
2. 让系统先依赖某个事件源，再在候选池上做推荐

本设计用于冻结第一版 `系统自动推荐` 的正式方向。

## 2. 目标

第一版 `系统自动推荐` 的目标是：

- 不依赖本地事件库
- 能根据当前筛选条件，开放发现一批可讲的历史事件
- 再通过本地约束收敛成 3-5 个可确认的 `Topic Candidate Card`
- 保持与 `Event Registry / Candidate Cache / Topic Package` 的现有合同兼容

它不是：

- 事件库浏览器
- 题库排序器
- 事实检索系统
- 下游阶段的内容规划器

## 3. 备选路线

### 方案 A：纯开放发现

定义：

- LLM 直接基于筛选条件开放生成候选事件与讲法
- 本地层只负责归一化、去重、疲劳惩罚、风险约束和最终展示

优点：

- 与现有 [topic-stage-design.md](docs/architecture/topic-stage-design.md) 完全一致
- 不需要先建设本地事件库或外部检索
- 实现路径最短，最适合当前阶段

缺点：

- 可控性弱于“有正式事件源”的推荐器
- 候选质量更依赖 prompt 设计和本地约束质量

### 方案 B：开放发现 + 外部检索增强

定义：

- 先从外部知识源拿到一批事件线索
- 再让 LLM 在这些线索基础上产出候选讲法

优点：

- 比纯生成更稳
- 可减少模型纯靠内部记忆带来的重复与漂移

缺点：

- 当前项目尚未定义正式外部数据源
- 会同时引入检索质量、授权和归因问题
- 超出第一阶段范围

### 方案 C：本地事件库驱动推荐

定义：

- 先维护本地历史事件池
- 再根据筛选条件与记忆约束在池中排序和组合

优点：

- 可控性最高
- 候选覆盖、冷却、去重更容易管理

缺点：

- 与现有正式设计冲突
- 会把“系统自动推荐”变成“本地题库推荐”
- 前置建设成本高，且会挤压当前 `topic + script` 第一阶段目标

## 4. 选型结论

第一版选择 **方案 A：纯开放发现**。

理由：

1. 它与正式文档一致。
2. 它不要求我们先建设一个新的事件源系统。
3. 它能在当前阶段最快形成产品闭环。
4. 当前项目已经有 `Event Registry`、`Candidate Cache`、`runtime harness` 和 LLM 交互日志，足够支撑第一版开放发现推荐。

明确不选：

- 不把 `系统自动推荐` 做成本地事件库排序器
- 不在第一版就引入外部检索

## 5. 第一版正式定义

第一版 `系统自动推荐` 定义为：

> 由 LLM 基于当前筛选条件进行开放式历史题材发现，再由本地约束层完成归一化、去重、疲劳惩罚、风险筛除与候选收口的推荐器。

其中：

- **开放发现** 负责“想到什么值得讲”
- **本地约束** 负责“哪些能留、哪些要淘汰”
- **用户确认** 负责“最终进入哪个讲法”

## 6. 推荐器分层

### 6.1 输入层

第一版输入只允许来自当前页面的系统筛选：

- `历史时期`
- `叙事张力`

它们会先被映射成一份正式推荐请求：

- `canonical_name`
- `summary`
- `core_conflict`
- `strong_scene`
- `source_hint`
- `recent_usage_hint`
- `tags`

注意：

- 这份输入是“推荐意图 seed”
- 不是固定事件
- 也不是最终 `Topic Package`

### 6.2 开放发现层

LLM 任务：

- 基于推荐意图 seed，提出一批值得讲的历史事件与角度
- 这些输出必须仍然落在 `Topic Candidate Card` 合同范围内

LLM 不负责：

- 直接写成脚本
- 输出下游对象
- 决定最终被用户确认的单一主题

### 6.3 本地约束层

本地层负责：

- `Event Registry` 归一化
- candidate 合同校验
- 事件身份去重
- 近期重复惩罚
- 人物疲劳惩罚
- 风险候选淘汰
- 槽位不足时最多补位一次

本地层不负责：

- 改写候选的叙事语义
- 二次生成整稿
- 把推荐器做成新的多轮裁判系统

### 6.4 输出层

输出对象仍然是：

- 3-5 个 `Topic Candidate Card`

用户确认之后才进入：

- `Topic Package`
- `Topic Delivery Pack`
- `Script Input Bundle`

## 7. 与 Event Registry 的关系

`Event Registry` 在该方案中的角色是：

- 事件身份账本
- 归一化与去重层

它不是：

- 默认候选来源
- 本地事件题库
- 系统自动推荐的主语料池

也就是说：

- 推荐候选可以是开放发现出来的新事件
- 只要进入主链路，就必须被归一化到 `Event Registry`
- 如无匹配，则允许创建新的 `provisional` 事件

## 8. 与 Candidate Cache 的关系

`Candidate Cache` 的角色是：

- 当前任务内推荐候选的短期缓存层

它不承担：

- 长期题库
- 推荐主来源
- 事件身份定义

第一版规则：

1. 当前任务内生成过但未确认的高质量候选可以缓存。
2. 缓存候选可参与同任务后续轮次的优先复用。
3. 跨任务复用必须重新经过去重、疲劳和风险约束。
4. 不允许把缓存层直接暴露成“系统自动推荐候选池”。

## 9. 推荐链路

第一版正式链路如下：

```text
系统筛选条件
-> 推荐意图 seed
-> LLM 开放发现
-> Topic Candidate Card 初稿
-> Event Registry 归一化
-> 去重 / 疲劳 / 风险筛除
-> 3-5 个推荐候选
-> 用户确认
-> Topic Package
```

如候选不足：

```text
首轮候选不足
-> 仅允许补位一次
-> 重新归一化与筛除
-> 输出最终候选
```

不允许：

- 无限重试
- 多轮竞赛式生成
- 为了补足数量而放松合同边界

## 10. Prompt 角色

第一版 prompt 的职责是：

- 在给定筛选意图下提出“值得讲”的事件和讲法
- 尽量让候选之间保持差异
- 输出仍受 `Topic Candidate Card` 结构约束

prompt 不负责：

- 事件身份最终归一
- 历史冷却管理
- 用户偏好长期记忆
- 下游文案或分镜规划

这意味着：

- 推荐质量的提升，不应只靠不断加 prompt 负担
- 本地约束层必须继续存在，并承担稳定性责任

## 11. 可观测性要求

第一版必须保留现有日志与 trace 能力：

- `graph-trace-summary.json`
- `runtime-diagnostics.json`
- `llm-interactions/*.md`

每一轮系统推荐至少要可回答：

1. 当前输入 seed 是什么
2. 模型原始输出是什么
3. 为什么某些候选被保留或淘汰
4. 最终交给用户的是哪几个候选

## 12. 非目标

本设计当前不解决：

- 外部搜索 / RAG / 向量检索
- 本地历史事件大全建设
- 人工 curated 题库
- 推荐多样性全局最优化
- 跨账号长期兴趣建模

## 13. 实施建议

建议分两步落地：

### 第一步：语义收口

- 正式定义“推荐意图 seed”字段
- 让 `系统自动推荐` 输入不再是固定事件
- 保持开放发现 + 本地约束的现有主链路

### 第二步：约束增强

- 在本地层补足重复惩罚与疲劳惩罚
- 让推荐器真正具备“开放发现但不乱漂”的可控性

第一步已经开始落地：

- 前端固定 `晏子使楚` seed 已移除
- LLM 交互日志已补齐

## 14. 成功标准

第一版完成的标志：

1. `系统自动推荐` 不再依赖任何固定样例事件。
2. 推荐链路的输入、模型输出与最终候选都可观测。
3. 推荐语义与 `Event Registry`、`Candidate Cache`、`Topic Package` 不冲突。
4. 用户能在不接触事件库的情况下，直接拿到稳定可确认的候选主题。
