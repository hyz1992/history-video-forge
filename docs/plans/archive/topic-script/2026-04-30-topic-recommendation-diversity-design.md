# 2026-04-30 Topic 推荐多样性增强设计

## 1. 背景

当前 `系统自动推荐` 已经解决了两个基础问题：

- 不再固定返回单一样例事件
- 候选标题不再大面积停留在“王朝更迭 / 古代战争 / 百家争鸣”这类抽象题桶

但连续真实运行后，新的质量问题已经暴露得很明确：

- 候选会快速塌缩到少数高热事件
- 单轮内部虽然没有完全重复，但多轮之间反复出现同一批事件
- 当前本地 fatigue 只做轻量排序，无法真正拉开最终交付的 `3` 个候选

最近 5 轮真实样本里，`商鞅变法 / 焚书坑儒 / 鸿门宴` 明显高频重复，说明问题已经不是“候选不具体”，而是“候选不够分散”。

## 2. 目标

本设计的目标是：

- 在不引入本地事件库的前提下，提高系统自动推荐的事件多样性
- 保持当前“开放发现”路线，不把系统推荐改造成本地题库排序器
- 不通过本地字符串匹配、关键词黑名单或伪语义规则糊弄多样性
- 不让本地后处理抢做只有 LLM 才能完成的语义选择工作

本设计不解决：

- 外部检索增强
- 本地历史事件大全建设
- 跨账号长期兴趣建模
- 下游 `script` 阶段的多样性问题

## 3. 新增约束

设计与实现必须服从以下两条仓库级约束：

1. prompt 约束不能冗余、打架或重复表达  
   新增 prompt 前，必须先确认它的职责边界，不允许多个 prompt 重复承担同一职责。

2. 本地逻辑不能抢做 LLM 才能完成的语义判断  
   本地只允许做结构、缓存、去重、疲劳惩罚、合同与运行时编排相关工作，不允许用字符串匹配或关键词黑名单冒充语义校验。

## 4. 方案对比

### 方案 A：单阶段扩池 + 本地选 3

做法：

- `candidate-builder` 一次生成 `8-10` 个候选
- 本地继续做去重、fatigue、排序
- 直接取前 `3` 个作为最终推荐

优点：

- 实现最轻
- 不引入第二个 LLM 调用

缺点：

- 本地无法判断“这两个题虽然不是同一事件，但是否仍然过于同质”
- 一旦原始池本身塌缩，本地仍然只能在坏池子里挑

结论：

- 可作为过渡方案
- 但不适合作为正式长期方案

### 方案 B：多轮排除式生成

做法：

- 每轮只生成 `1-2` 个
- 下一轮把已选事件和近期高频事件作为排除上下文，再继续生成
- 最后拼出 `3` 个结果

优点：

- 多样性最强
- 语义选择仍然由 LLM 完成

缺点：

- LLM 调用次数明显增加
- 链路变长，时延和成本都更高
- prompt 会更容易膨胀

结论：

- 可行，但第一版偏重

### 方案 C：两阶段 LLM，推荐

做法：

1. `topic.candidate-builder`
   - 负责开放发现
   - 一次生成 `8` 个原始候选
2. 本地结构层
   - 做事件 identity 归一化
   - 做精确去重
   - 标注 fatigue 信息
   - 形成 selector 候选池
3. `topic.selector`
   - 新增第二个 LLM prompt
   - 从候选池中选出最终 `3` 个更分散的候选

优点：

- “找题”和“挑题”分工明确
- 不要求本地做语义裁判
- prompt 不容易打架，因为职责被拆开
- 比多轮排除式生成更轻

缺点：

- 比当前链路多一次 LLM 调用
- 需要新增一个 selector 合同

结论：

- 这是当前最符合仓库约束的方案
- 也是本设计的推荐方案

## 5. 选型结论

本设计选择 **方案 C：两阶段 LLM**。

核心原因：

1. 多样性本质上仍然是语义选择问题，不应该由本地 if/else 接管
2. 只靠一个 builder prompt 同时承担“开放发现 + 最终多样性裁决”会继续造成 prompt 负担膨胀
3. 拆出 `topic.selector` 后，可以把“多样性选择”集中到一个职责单一的 prompt 中完成

## 6. 正式定义

增强后的 `系统自动推荐` 定义为：

> 先由 `topic.candidate-builder` 进行开放发现，生成一个结构化候选池；再由本地结构层完成归一化、去重与历史疲劳标注；最后由 `topic.selector` 从候选池中挑出最终 `3` 个事件不同、切口更分散的候选结果。

其中：

- builder 负责“发现可能的题”
- selector 负责“从池子里挑开”
- 本地层负责“结构事实与运行时约束”

## 7. 组件职责

### 7.1 `topic.candidate-builder`

职责：

- 基于当前 recommendation seed 开放发现历史事件
- 一次产出 `8` 个原始候选
- 尽量覆盖不同事件、不同冲突场景、不同人物位置

不负责：

- 最终 3 选 3
- 历史疲劳控制
- 候选最终保留策略

### 7.2 本地结构层

职责：

- 事件 identity 归一化
- 同 event identity 精确去重
- 读取近期 round history / candidate cache
- 计算 fatigue 信息
- 构造 selector 输入
- 校验 selector 输出是否合法

不负责：

- 判断两个不同事件是否“语义上太像”
- 通过字符串匹配判断题材价值
- 本地替代 LLM 做最终语义裁决

### 7.3 `topic.selector`

职责：

- 从结构化候选池中选出最终 `3` 个候选
- 优先保证事件不同
- 尽量拉开冲突类型、叙事切口和场景分布
- 避免把最终结果继续收敛到同一批高频热点

不负责：

- 再次开放生成新候选
- 输出脚本或下游对象

## 8. 数据流

正式链路如下：

```text
系统筛选条件
-> recommendation seed
-> topic.candidate-builder
-> 原始候选池（8个）
-> 本地归一化 / 去重 / fatigue 标注
-> topic.selector
-> 最终 3 个候选
-> 用户确认
-> Topic Package
```

## 9. selector 输入与输出

### 输入

`topic.selector` 至少接收：

- 当前 recommendation seed
- 当前候选池
- 每个候选的：
  - candidate id
  - normalized event identity
  - title
  - one_line_angle
  - family / scope
  - fatigue score
  - recently seen 标记
- 最近 2-3 轮已推荐事件的 identity 列表

### 输出

只允许输出：

- 最终选中的 `3` 个 candidate id
- 可选的简短选择说明

selector 不允许输出新的 candidate，不允许发明新对象。

## 10. repair 机制

如果 selector 因候选池过窄而无法稳定选满 `3` 个：

- 允许触发一次受控 repair
- repair 的输入包括：
  - 当前 recommendation seed
  - 已保留的 candidate id / event identity
  - 明确排除列表
  - 仍需补齐的槽位数

repair 仍然由 LLM 负责语义补位，本地只负责编排。

不允许：

- 无限重试
- 多轮竞赛式生成
- 为了补齐数量而降低候选合同要求

## 11. 本地层允许与禁止

### 允许

- 精确 identity 去重
- fatigue 打分
- 候选池裁剪
- selector 输出结构校验
- fallback 编排

### 禁止

- 根据标题包含某些词就判定“同质”
- 根据关键词黑名单剔除“热点事件”
- 用字符串规则冒充“语义多样性”
- 本地硬编码“某些题必须少出现”

## 12. prompt 设计原则

### builder prompt

只负责：

- 发现更多候选
- 尽量覆盖不同事件

不负责：

- 最终 3 选 3
- 复杂疲劳策略

### selector prompt

只负责：

- 从候选池中挑出更分散的最终集合

不再要求 builder 自己同时承担“开放发现 + 最终裁决”，从而避免 prompt 冗余和职责打架。

## 13. 验证标准

该方案落地后，至少要满足：

1. 连续多轮同 seed 下，最终结果不再长期塌缩到 2-3 个高频事件
2. 本地层没有新增伪语义判断逻辑
3. 新增 selector prompt 后，builder prompt 没有继续膨胀为“万能 prompt”
4. trace 中可以清楚回答：
   - builder 产了几个候选
   - 本地去重后还剩几个
   - selector 最终选了哪几个
   - 是否触发 repair

## 14. 成功标准

如果连续真实运行时出现以下结果，可视为方案成功：

1. 候选仍保持具体历史事件，而不是回退到抽象题桶
2. 多轮同 seed 下最终结果的事件重复率明显下降
3. selector 能在不依赖本地语义规则的前提下，把最终 3 个候选拉开
4. 当前开放发现架构仍然成立，没有被偷偷改造成本地题库排序器
