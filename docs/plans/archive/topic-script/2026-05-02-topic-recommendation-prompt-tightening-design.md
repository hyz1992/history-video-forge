# 2026-05-02 Topic Recommendation Prompt Tightening Design

## 1. 背景

最近的真实回归已经证明两件事同时成立：

1. 当前 `builder -> selector` 两阶段链路已经能在真实运行中稳定跑通。
2. `topic` 的最终 3 个候选在连续多轮下已经明显优于早期版本，但 builder 的原始候选池仍然存在两个持续性问题：
   - 输出结构仍不够稳定，经常漂移到非正式 JSON 形态
   - 对宽 seed，原始 8 候选仍容易反复收敛到少数高频事件，最后主要依赖 selector 和 fatigue 去兜底

中国题材的最近一次真实 5 轮回归尤其说明了这一点：

- 最终结果已经不再直接重复
- 但原始候选池仍频繁回到 `商鞅变法 / 焚书坑儒 / 陈胜吴广起义`
- builder 已经看到了 `recent_event_memory`，但它更多是在复用 `event_identity`，还没有充分履行“源头扩池”的职责

这意味着下一步优化不该再去动本地后处理，而应该在 prompt 层做一次范围克制、边际收益明确的收紧。

---

## 2. 这次要解决什么

本次只解决 3 个 prompt 层问题：

1. builder 输出结构仍漂移
2. builder 对近期高频事件的源头避让不够强
3. selector 仍偶尔返回超过 3 个 id

本次不解决的问题：

- 不重做两阶段架构
- 不增加第三个 prompt 阶段
- 不引入任何本地伪语义判断
- 不上复杂的朝代配额系统
- 不改 UI seed 入口

---

## 3. 设计目标

本次优化应满足：

1. 提高 builder/selector 的正式合同遵守率
2. 让 builder 在看到 `recent_event_memory` 时，更主动地把原始候选池扩散到不同事件，而不是继续把近期高频事件塞满 8 个槽位
3. 保持 prompt 总体长度和认知负担可控，避免约束冗余和 prompt 打架

成功标准不是“规则更多”，而是：

- 原始 8 候选的事件分布更散
- 结构漂移更少
- selector 更少出现“多给 4 个 id，再由 runtime 截断”的情况

---

## 4. 可选方案

### 方案 A：只收紧结构合同

做法：

- builder 明确只输出数组，不允许再包 `TopicCandidateCard`
- builder 明确 `viral_rubric` 只能使用正式字段
- selector 明确只能返回 3 个 id

优点：

- 风险最低
- 不容易造成 prompt 膨胀

缺点：

- 只能解决结构漂移
- 对“原始候选池仍收敛到同一批高频事件”帮助有限

### 方案 B：收紧结构合同 + 轻量强化 builder 的源头扩池职责

做法：

- 包含方案 A
- 另外在 builder 中新增一小段、非常克制的开放发现优先级：
  - 若近期事件已高频出现，不要继续让它们占据原始 8 槽位的大头
  - 对宽 seed，优先拉开朝代、冲突类型、人物结构
  - 但不使用硬配额，不发明复杂计分体系

优点：

- 对当前问题命中更准
- 边际收益最好
- 仍能控制 prompt 增量

缺点：

- 需要写得很克制，否则容易和已有“多样性/时代边界/具体事件化”约束重叠

### 方案 C：对宽 seed 引入显式分布配额

做法：

- 要求 builder 在宽 seed 下强制覆盖多个朝代和多个冲突类型

优点：

- 对“分布偏窄”最直接

缺点：

- prompt 很容易过重
- 容易牺牲自然度
- 也最容易和现有约束打架

---

## 5. 推荐方案

推荐采用 **方案 B**。

原因：

1. 现在的主问题已经不是“最终 3 个老是重复”，而是“原始候选池的扩散能力不够”
2. 这件事主要应该由 builder 承担，而不是继续往 selector 或本地逻辑上加补丁
3. 方案 B 能直接打到问题核心，同时不至于把 prompt 推到过重

---

## 6. 正式设计

### 6.1 builder：收紧输出格式合同

只新增最小必要约束：

- 必须直接输出候选数组
- 不得再包 `TopicCandidateCard` 外层对象
- `viral_rubric` 只能使用正式字段
- 不得自定义额外评分键

这里的目标是减少结构漂移，而不是新增更多业务规则。

### 6.2 builder：轻量强化“近期高频事件不要占满原始池”

只新增一小段源头扩池约束：

- 若 `recent_event_memory` 中某些事件已经高频出现，优先扩展到其他事件
- 不要继续让这些近期事件占据原始 8 候选的大多数槽位
- 对宽 seed，优先拉开：
  - 朝代分布
  - 冲突类型
  - 人物/制度/战争/外交/思想事件的叙事结构

但这里明确不做：

- 不做硬性配额表
- 不要求每轮必须覆盖固定数量的朝代
- 不新增复杂打分体系

### 6.3 selector：只补“必须且只能返回 3 个 id”

selector 现有职责已经足够，不再继续加一堆规则。

只做一处收口：

- 把“必须且只能返回 3 个候选 id”写得更硬、更显眼
- 明确多于 3 个也算违规

除此之外，不再继续增加 selector 约束，避免两阶段 prompt 都变成超长清单。

---

## 7. 为什么不继续加更多 prompt 规则

这次设计刻意克制，是因为已经接近边际效应拐点。

再继续大量加规则，会带来 3 个风险：

1. prompt 冗余
2. builder 与 selector 职责重叠
3. 宽 seed 下模型为了服从太多显式条款，反而退化成机械凑分布

因此这次的原则是：

- 只补当前真实回归已经反复暴露的问题
- 不预防性加一大堆尚未证明有效的条款

---

## 8. 预期效果

如果本次 prompt 收紧有效，下一轮真实回归应看到：

1. builder 更少输出 `TopicCandidateCard` 包装对象
2. `viral_rubric` 自定义键明显减少
3. 原始 8 候选里，近期高频事件占比下降
4. 宽 seed 下的候选分布更自然拉开
5. selector 更少返回 4 个或更多 id

---

## 9. 结论

当前最值得做的不是继续扩本地逻辑，也不是上复杂配额系统，而是：

- 轻量收紧 builder 输出结构合同
- 轻量强化 builder 的源头扩池职责
- 对 selector 只做最小的“严格 3 id”收口

这条路线的优点是：

- 命中真实问题
- 变更面小
- 风险可控
- 不会把 prompt 推到明显过重
