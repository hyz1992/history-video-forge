## Step 3：多模型、多供应商切换（P0 基础合同）

### 目标

解除业务逻辑和单一供应商的硬绑定。第一阶段覆盖 LLM、生图、生视频和 TTS，并为 ASR、BGM、SFX 等同类能力预留扩展方式。

### 用户价值

- 用户可以选择不同模型平衡速度/质量/成本。
- 管理员可以接入新供应商而不修改 pipeline 主流程。
- 历史运行可以追溯实际使用的配置。

### 当前问题（已验证）

- LLM provider 只有 `stub | openai` 两种，硬编码在 [env.ts](../../backend/src/config/env.ts)。
- DashScope 凭据通过 `process.env.ALIYUN_DASHSCOPE_API_KEY` 直接读取，散落在 [assets-run.service.ts](../../backend/src/modules/assets/assets-run.service.ts)、[publish.controller.ts](../../backend/src/modules/publish/publish.controller.ts)。
- 没有 Run Configuration Snapshot——每次运行不记录实际使用的 provider、model、参数。
- 没有 Usage/Cost Record——token、图片、秒数、费用不被持久化追踪。
- Assets 阶段已有 `AssetProviderAdapter` 抽象（image/video/tts/sfx/bgm），但 LLM 层缺少同类抽象。

### 范围

- Capability/Provider/Model/Capability Adapter/Provider Adapter/Model Profile/Routing Policy/Credential Reference/Run Configuration Snapshot/ProviderJob/Usage Cost Record。
- 统一的是治理、路由、快照和错误语义，不是强迫四种能力共享一个臃肿请求对象。

### 非目标

- BYOK（用户自带 key）。
- 通用 AI Gateway。
- 插件市场。
- 自动模型选择（agent 自主选择）。

### 前置依赖

- Task 8.5-9 完成（ProviderJob 中断恢复、文件提交协议）。`已验证`（未完成）。
- V2 P0.1/P0.2 完成（auth + 项目隔离，提供 user 上下文）。

### 核心实体/合同

- `RunConfigurationSnapshot`：记录每次运行的不可变配置（provider、model、参数、prompt 版本、预算）。
- `UsageCostRecord`：请求级 token/image/sec/char/费用。
- `ProviderModel`：模型目录（代码配置 + 数据库配置混合）。
- `ProviderCredential`：凭据引用（env var 名称，不存明文）。
- `CapabilityRouter`：运行时选择 provider + model + credential。

### 重大审查点

- 能力合同冻结（Capability/Provider/Model 的边界）。
- 凭据策略冻结（env 引用 vs 加密存储）。
- fallback 循环保护。
- 付费任务幂等提交（所有 provider adapter 遵守同一合同）。

### 最小可交付版本

- LLM gateway 扩展为多 provider。
- provider 凭据从 env 迁移到 credential reference。
- 每次运行写入 RunConfigurationSnapshot。
- 至少一种能力（LLM 或 image）可在真实/mock 间配置切换。

### 验收方式

- 新增同类供应商不修改 pipeline 主流程。
- 每种能力至少可在一个真实实现与 mock/local 实现间配置切换。
- 历史运行能够解释实际使用的配置。
- provider 失败不会产生无限重试、错误 fallback 或重复付费。
- 凭据不会泄漏到浏览器、trace、快照和错误响应。

### 已知风险

- R3-1：能力过度统一，导致 LLM/image/video/tts 共享臃肿请求对象。
- R3-2：fallback 循环导致无限重试。
- R3-3：付费任务在未知提交状态时被重提。
- R3-4：凭据泄漏到日志或快照。
- R3-5：模型目录配置错误导致 pipeline 阻塞。

### 启动条件

- P0.1/P0.2 完成并通过验收。
- Task 8.5-9 关闭（文件提交协议 + ProviderJob 中断恢复）。
- 能力合同设计文档通过审查。

## Step 4：选题筛选条件扩充（P1）

### 目标

让推荐从"少量朝代 + 叙事情绪"升级为真正可组合、可维护、能影响生成结果的筛选系统。

### 用户价值

- 用户可以按朝代、人物类型、事件类型、冲突类型等维度精准选题。
- 用户可以排除已做过的题材或敏感主题。

### 当前问题（已验证）

- 当前 topic recommendation 没有结构化筛选维度（代码中不存在 dynasty、era、character_type 等字段）。
- 筛选不进入 prompt、fingerprint、曝光记录。

### 范围

- 固定枚举（朝代、人物类型、事件类型）。
- 层级词表（主题母题）。
- 动态配置（知名度、史料可靠性）。
- 自由输入（排除项）。
- 硬过滤 vs 软偏好 vs 负向偏好。
- 筛选进入 prompt、候选 cache key、fingerprint、曝光记录、排序。

### 非目标

- 实时外部数据源。
- 独立搜索引擎。
- 基于用户行为的个性化推荐。

### 前置依赖

- 与 Step 5（事件库）字段协调设计。
- V2 P0 完成（auth 提供用户上下文，支持用户级筛选偏好）。

### 核心实体/合同

- `TopicFilter`：筛选条件对象。
- `RecommendationCandidateCache` 扩展：新增筛选维度字段。
- 现有 fingerprint 算法扩展：纳入筛选维度。

### 重大审查点

- 筛选模型与事件库字段协调。
- 旧项目、旧候选、旧指纹兼容。
- 筛选不产生大量无结果或矛盾组合。

### 最小可交付版本

- 朝代、人物类型、事件类型、冲突类型、主题母题五个核心维度。
- 筛选进入请求和运行快照。
- 筛选可观察地影响 prompt 和 fingerprint。

### 验收方式

- 筛选条件进入请求和运行快照并可观察地影响结果。
- 非法组合有明确反馈。
- 多轮推荐继续遵守跨重启去重和疲劳惩罚。
- 旧项目恢复仍兼容。

### 已知风险

- R4-1：筛选组合形成大量无结果状态。
- R4-2：筛选不实际影响 prompt，变成假控件。
- R4-3：旧指纹不兼容导致去重失效。

### 启动条件

- Step 5 字段设计同步（避免先造无法映射事件数据的词表）。
- 筛选模型设计文档通过审查。

## Step 5：事件库与自定义选题（P1）

### 目标

形成三个平等但最终汇入同一 Topic Package 冻结流程的选题入口：自动推荐、事件库、自定义选题。

### 用户价值

- 用户可以从结构化事件库浏览和选择。
- 用户可以输入自定义命题。

### 当前问题（已验证）

- 事件库和自定义入口仍在 backlog。
- 当前 EventRegistryEntry 主要是 LLM 输出的归一化记录，不是正式事件库。

### 范围

- Event 与 Narrative Angle 分离。
- 规范名称、别名、时间范围、地点、人物关系。
- 史料来源、来源级别、争议点、可信度。
- 系统内置条目、管理员维护条目、用户私有草稿边界。
- 自定义输入生成 Event/Angle 引用、fingerprint、合法 Topic Package。

### 非目标

- 把 LLM 临时输出当史实数据库。
- 外部历史 API 接入。
- 用户协作编辑事件库。

### 前置依赖

- 与 Step 4 字段协调设计。
- V2 P0 完成。

### 核心实体/合同

- `EventLibraryEntry`：正式事件库条目（区别于 EventRegistryEntry）。
- `EventLibraryAngle`：事件的多选题角度。
- `CustomTopicDraft`：自定义选题草稿。

### 重大审查点

- EventLibrary 与 EventRegistry 关系（避免双真相源）。
- Topic Package 合同不被破坏。
- 相同角度不会因换句话说而无限重复。

### 最小可交付版本

- 事件库浏览、搜索、详情预览。
- 自定义输入生成 candidate。
- 三入口进入同一后续链路。

### 验收方式

- 三种入口可追溯到来源并进入同一后续链路。
- 同一事件的不同角度不会被错误合并。
- 自定义选题绕过事实风险检查被拒绝。

### 已知风险

- R5-1：EventLibrary 与 EventRegistry 双真相源。
- R5-2：自定义选题绕过事实风险。
- R5-3：相同角度因换句话说而无限重复。

### 启动条件

- Step 4 字段设计同步。
- EventLibrary 数据模型设计通过审查。

## Step 6：用户偏好、生成策略与成本控制（P1）

### 目标

把生成偏好变成正式、分层、可解释的配置。

### 用户价值

- 用户可以设置"优先 Remotion"、"质量优先"等策略。
- 用户可以看到运行成本估算。

### 当前问题（已验证）

- 配置散落在 env 和页面临时开关。
- 没有运行快照，历史运行无法解释实际使用的配置。

### 范围

- 视频 API/Remotion 路线。
- 质量/速度/成本策略。
- provider/model 允许范围、fallback 许可、预算上限。
- 画幅、分辨率、时长、视觉风格、字幕、语言、音色、音频偏好。
- 预算软硬限制。
- 配置优先级合并。
- 运行前估算、运行中累计、运行后实际成本。
- 修改偏好只影响未来运行，历史运行保留不可变快照。

### 非目标

- 月度计费。
- 套餐限制。
- 用户级硬预算（第一版软提示）。

### 前置依赖

- Step 3 完成（多供应商基础，提供 provider/model 选择能力）。
- V2 P0 完成。

### 核心实体/合同

- `UserPreference`：用户生成偏好。
- `ResolvedRunConfiguration`：合并后的运行配置。
- 与 `RunConfigurationSnapshot` 关联。

### 重大审查点

- 配置优先级：系统硬限制 > 管理员允许范围 > 用户默认 > 项目覆盖 > 单次运行覆盖。
- 配置合并不产生无效模型组合。
- 历史运行保留不可变快照。

### 最小可交付版本

- 用户偏好实体。
- 配置优先级合并。
- 运行前估算/运行后实际成本。
- 策略切换 UI 说明质量、速度、成本差异。

### 验收方式

- 同一输入在不同策略下产生可解释的路由差异。
- 非法或超预算配置被后端拒绝。
- 历史记录不随默认配置变化。
- 实际执行与 UI 展示一致。

### 已知风险

- R6-1：配置合产生无效模型组合。
- R6-2：历史运行随默认配置变化（违反不可变）。
- R6-3：预算控制过严导致生成中断。

### 启动条件

- Step 3 完成（多供应商基础）。
- 用户偏好数据模型设计通过审查。

## Step 7：Prompt 代码资产治理（P2）

### 目标

让所有生产 prompt 可发现、可版本化、可测试、可追溯。

### 用户价值

- prompt 修改可以定位影响面并回归。
- 旧运行可以解释其 prompt 版本。

### 当前问题（已验证）

- prompt 位于 `harness/prompts/`，有基本 registry，但无语义版本、无输入/输出 schema、无运行时 hash。
- 用户原始方向（prompt 不属于 harness）与 AGENTS.md 规定冲突。

### 范围

- prompt ID、语义版本、语言、阶段、能力、owner。
- 输入 schema、输出 schema、模型兼容性、变量清单。
- system/developer/user 消息结构。
- 变更说明、废弃策略、兼容期。
- golden fixtures、结构测试、质量回归样本。
- 运行快照记录 prompt ID、版本、hash。
- 迁移方案比较（保留 harness/prompts vs 迁移到顶层）。

### 非目标

- prompt A/B testing。
- prompt marketplace。
- 自动 prompt 优化。

### 前置依赖

- 与 Step 8（LLM 性能）互相提供数据，但实现拆开。
- V2 P0 完成。

### 核心实体/合同

- `PromptMetadata` 扩展：新增 `semanticVersion`、`inputSchema`、`outputSchema`、`changeLog`。
- `RunConfigurationSnapshot` 记录 `promptId`、`promptVersion`、`promptHash`。

### 重大审查点

- 双目录冲突解决（harness/prompts vs 顶层 prompts/）。
- 不存在双真相源。
- 迁移时同步更新规范、注册表、loader、测试、构建、文档。

### 最小可交付版本

- prompt registry 扩展元数据。
- 运行快照记录 prompt 版本。
- golden fixtures 回归。

### 验收方式

- 可以列出全部生产 prompt 及调用方。
- 任何 prompt 修改都能定位影响面并回归。
- 旧运行可解释其 prompt 版本。
- 不存在双目录双真相源。

### 已知风险

- R7-1：迁移过程中双真相源。
- R7-2：prompt 版本不向后兼容导致历史运行不可重放。
- R7-3：golden fixtures 不覆盖真实场景。

### 启动条件

- 双目录冲突解决方案通过审查。
- Prompt 治理设计文档通过审查。

## Step 8：LLM 速度、质量和结构化输出优化（P2）

### 目标

解决当前 GLM-4.7/GLM-5 链路"能跑通但等待很慢"的问题。

### 用户价值

- 生成速度提升。
- 质量不下降。

### 当前问题（推断）

- 全链路统一大模型。
- 无 benchmark。
- 等待时间长。

### 范围

- 覆盖真实阶段的 benchmark（首 token 延迟、总耗时、P50/P95、token、结构成功率、质量、成本）。
- 分档模型。
- structured output 比较（原生 vs tool_call vs json_object）。
- 上下文精简。
- 缓存。
- 并行。
- 流式。
- 小模型+大模型审查评估。

### 非目标

- 训练自有模型。
- agent 自主选择模型。
- 牺牲质量换速度。

### 前置依赖

- Step 3 完成（多 provider 基础）。
- Step 7 提供 prompt 版本追踪（可选，但有助于 benchmark）。

### 核心实体/合同

- `BenchmarkResult`：benchmark 结果记录。
- 与 `UsageCostRecord`、`RunConfigurationSnapshot` 关联。

### 重大审查点

- benchmark 覆盖真实阶段，不是短 prompt。
- 同一基准集的速度/结构/质量/成本共同支持优化决策。
- 不因为快而明显降低脚本质量。

### 最小可交付版本

- benchmark 基线。
- 至少一个优化路径验证（同一基准集对比）。

### 验收方式

- 优化方案由同一基准集的速度、结构成功率、质量和成本共同支持。
- 不能因为快而明显降低脚本质量。
- 不能因为结构稳定继续接受不可用等待时间。

### 已知风险

- R8-1：benchmark 不覆盖真实场景。
- R8-2：优化降低内容质量。
- R8-3：小模型+大模型审查反而增加调用次数。

### 启动条件

- benchmark 设计文档通过审查。
- Step 3 完成。

## Step 9：历史内容策略配置化（P2）

### 目标

先把历史故事模式做扎实，再提炼可供相近故事模式切换的内容策略。

### 用户价值

- 扩展相近故事模式（如神话）时主要新增配置，不复制 pipeline。

### 当前问题（推断）

- 领域策略与 pipeline 稳定合同耦合。

### 范围

- pipeline 稳定合同与领域策略分离。
- 模式资产（prompt 组合、few-shot、词表、默认配置、UI 文案）。
- 历史模式（史料来源、争议、人物、时代、事实风险、叙事、视觉约束、质量基线）。
- 策略 ID、版本、运行快照。

### 非目标

- 多题材并行运营。
- 配置任意键值袋（必须有 schema）。

### 前置依赖

- Step 7 完成（prompt 治理提供资产基础）。
- 历史故事达到合格质量线。

### 核心实体/合同

- `ContentStrategy`：内容策略对象。
- 策略 ID、版本。
- 运行快照记录策略版本。

### 重大审查点

- 历史主链路不退化。
- 新增相近策略时主要新增配置和领域资产。
- 配置有 schema、版本、测试。

### 最小可交付版本

- 历史模式策略提取为配置。
- 至少一个相近策略（如"人物传记"vs"事件叙事"）通过配置切换验证。

### 验收方式

- 历史主链路不退化。
- 新增一个相近策略时主要新增配置和领域资产，而不是复制 pipeline。
- 配置有 schema、版本、测试。

### 已知风险

- R9-1：配置化导致历史内容质量下降。
- R9-2：配置过度复杂变成任意键值袋。
- R9-3：策略切换破坏 pipeline 稳定合同。

### 启动条件

- 历史故事达到合格质量线（明确标准）。
- 历史内容策略配置化设计通过审查。

## Step 10：神话故事等相近模式（P3，最低优先级）

### 目标

只留扩展点和 backlog，不正式设计完整实现。

### 用户价值

- 未来可以扩展到神话故事领域。

### 当前问题

- 无（当前不启动）。

### 范围（未来）

- 史实、传说、文学改编和现代再创作的内容标记。
- 不同版本、地域、谱系、人物关系。
- 世界观、神力规则、角色一致性。
- 象征性画面与事实性陈述区分。
- 视觉策略和素材生成约束。
- 不把神话内容包装成确定历史事实。

### 非目标

- 当前不正式设计。
- 不提前编码。
- 不挤占历史故事质量建设。

### 前置依赖（启动前提）

- 历史故事已经达到明确的合格质量线。
- 历史内容策略已完成配置化并通过回归。
- 策略扩展不需要复制整条 pipeline。
- Topic Package 等稳定合同不需要被神话模式破坏。

### 核心实体/合同

- 复用 `ContentStrategy` 扩展点。
- 新增神话模式特定的 schema、validator、prompt 组合。

### 重大审查点

- 历史质量线明确。
- 配置化通过回归。
- 不破坏稳定合同。

### 最小可交付版本

- 神话模式 backlog 完整留痕。
- 扩展点在 Step 9 中明确预留。

### 验收方式

- 满足启动前提后才进入实现。
