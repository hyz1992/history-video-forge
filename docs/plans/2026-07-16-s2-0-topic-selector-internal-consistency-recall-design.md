# S2-0 Topic Selector 内部一致性召回窄设计

## 1. 背景

Task 17 的 Topic Selector 紧凑 verdict 已证明能够减少 completion 体积，并保持现有内部结论与下游合同不变；随后固定输入语义回放却连续出现风险召回 `0/3`。受控恢复完整 verdict 后，同一组固定输入仍为风险召回 `0/3`，同时两个 `none` 对照均保持正确。

因此，完整或紧凑 DTO 不是风险漏判的充分解释。失败发生在模型生成语义结论的阶段，不是 schema、parser、trace、selection、前端或下游传输阶段。

本设计只处理 Topic Selector 对候选**内部一致性**的召回，不扩张为史实核查，也不处理其他阶段质量问题。

## 2. 已确认的证据

### 2.1 可由 Selector 输入内部判定的漏判

固定样本中有两项高置信度内部一致性缺陷：

1. **靖康之变**：标题、冲突和 preview 明确区分宋徽宗禅位出逃与宋钦宗赴金营谈判，但 `one_line_angle` 用同一个“皇帝”串联两组动作，形成 `actor_role_mismatch`。
2. **鸿门宴**：内部材料只支持刘邦脱身和范增失望，标题却把这一刻升级为“天下归属已经注定”，形成 `overclaim_or_ambiguity`。

这两项都能通过横向比较 `title`、`one_line_angle`、`core_conflict`、`strong_scene` 与 `must_cover_preview` 得出，无需外部史料。

### 2.2 不适合作为当前硬召回标注的样本

“党锢之祸”的“永久禁止做官”“整个知识阶层的沉默”“清议传统彻底断绝”等绝对化说法，已经在候选的 `core_conflict` 或 `must_cover_preview` 中重复。Selector 收到的候选内部没有反证。

继续把该项作为“只检查候选内部是否互相支持”的硬召回标注，会要求 Selector 在缺少内部反证时执行外部史实判断，与当前正式职责边界冲突。因此该项应退出自动比较器的硬指标，但保留为人工观察记录，不把它改判为 `none`，也不通过本地规则重新分类。

### 2.3 工作样本与失败样本的差异

Task 16 的真实样本说明当前模型能够识别表层、显式的时代越界，也曾识别存在明确争议的主体归属；但它同时漏判了“败退亡国”相对于内部正文的结果升级。Task 17 又漏判主体合并和终局断言升级。

现有 prompt 虽然列出检查对象和 issue enum，但没有明确要求先把标题与切口中的主体、动作、结果和断言强度拆开，再逐项寻找内部支持。模型可以在同时承担排序任务时直接给出 `none`，而不完成关系级横向审查。

这形成一个可证伪假设：**在不改变 DTO、模型和调用策略的前提下，用短而明确的“原子断言—内部证据”审查顺序替代泛化检查措辞，可能改善两类内部关系缺陷的召回。**

## 3. 目标

1. 让 Selector 在排序前先完成逐候选的内部一致性审查。
2. 提高主体合并和结果/断言强度升级的召回。
3. 保持玄武门、巫蛊之祸两个 `none` 对照不被误报。
4. 保持紧凑 provider DTO、parser、选择逻辑、API 与下游合同不变。
5. 用最小固定输入 live 回放证伪或支持本设计，不用非 live 结果冒充语义质量证据。

## 4. 非目标与硬边界

- 不执行正式史实核查，不引入外部检索或史料库。
- 不新增任何形式的本地语义校验。
- 不使用关键词、字符串匹配、正则、黑名单、相似度、规则评分或本地启发式推导 `pass/risk`。
- 不读取候选文本自动生成或修正 annotation。
- 不把 semantic reviewer 升级为门禁或主链路动作。
- 不增加第三次 LLM 调用，不拆出新的审校阶段。
- 不修改 GLM-5.2、`thinking=disabled`、timeout、retry、repair 或默认 request budget。
- 不修改 shared schema、公开 API、前端、Topic Package 或任何 downstream 对象。
- 不恢复完整 verdict，不新增中间 claim/evidence 输出字段。
- 不在本任务中修改 Candidate Builder；本次只验证 Selector prompt 的单变量变化。

## 5. 方案选择

### 5.1 采用方案：评测边界修正 + prompt-only 原子断言审查

该方案分为两个低耦合动作：

1. 修正固定回放的硬指标范围，使其只包含 Selector 输入内部可观察的人工标注。
2. 只调整正式 Selector prompt 的判断顺序，要求模型在内部完成原子断言与证据映射，但不输出分析过程。

生产运行时只有 prompt 是语义变量；fixture 调整只修正评测口径，不进入生产路径。

### 5.2 暂不采用对比例子

第一轮不加入靖康、鸿门宴或其改写版本作为 few-shot 示例，避免针对固定样本过拟合、增加 prompt 冗余或诱导机械套用。如果原子审查协议被 live 回放否证，应先记录失败，不在同一任务中继续堆叠示例。

### 5.3 不采用中间结构字段

完整 verdict 的固定输入回放已经证明，增加逐候选状态和说明并不能恢复风险召回。再次增加 claim/evidence 字段会扩大 completion、破坏紧凑设计，并改变多个变量，不能形成干净实验。

## 6. Prompt 设计

正式 prompt 保持现有输出合同与 issue enum，只收敛“判断顺序”。模型应在内部执行以下步骤：

1. 对每个候选，先静默拆出标题和切口中的关键断言：具体主体、主体执行的动作、动作导致的结果以及断言强度。
2. 分别在 `core_conflict`、`strong_scene` 与全部 `must_cover_preview` 中寻找对应支持，不把 `risk_hints` 当成完整风险清单。
3. 如果同一个泛称主体串联的动作在内部材料中分别属于不同人物，标记 `actor_role_mismatch`。
4. 如果标题或切口声称确定性终局、灭亡、注定或同等级强结果，而内部材料只支持脱身、失败、受创或格局变化，标记 `overclaim_or_ambiguity` 或更准确的既有 issue。
5. 先确定 `consistency_issue`，再进行叙事质量排序，避免排序任务覆盖一致性审查。
6. 不输出上述拆解或思考过程，只按现有紧凑 DTO 返回结果。

Prompt 不应新增跨题材固定模板句，也不应重复堆叠同义口号。实现时优先改写现有判断顺序，而不是在多处重复追加约束。

## 7. Fixture 与比较器边界

### 7.1 硬指标

- 风险正例：靖康之变、鸿门宴，共 2 项。
- `none` 对照：玄武门之变、巫蛊之祸，共 2 项。
- 具体 issue enum 继续作为辅助一致率；主指标仍先看风险是否为非 `none`、对照是否保持 `none`。

### 7.2 党锢之祸处理

从固定 fixture 的 `annotations` 硬比较集合中移除党锢之祸，但在 fixture 说明和基线记录中保留：它是需要外部史实判断的人工观察，不属于本轮内部一致性门禁。

不得新增代码读取“永久”“彻底”“整个”等文本来决定它是否参与 gate，也不得根据候选内容动态切换 annotation。调整是一次明确、人工审查后的静态测试范围修正。

### 7.3 本地比较器允许做什么

本地回放只允许：

- 校验 fixture JSON 结构。
- 校验 annotation 引用的 candidate ID 确实存在。
- 比较人工静态 annotation 与 provider 返回的 `consistency_issue`。
- 统计覆盖数、请求数、结构结果和 usage。

本地回放不得读取候选正文来推导、补充或覆盖语义标签。

## 8. 验证设计

### 8.1 非 live 验证

按 TDD 顺序实施：

1. 先更新 prompt 约束测试，使旧 prompt 因缺少原子断言审查顺序而失败。
2. 最小调整 prompt，使测试通过。
3. 更新 fixture annotation 期望和回放统计测试，确认硬风险总数为 2、`none` 对照为 2。
4. 回跑受影响的 prompt、language、schema/parser、runtime 与 semantic replay 测试。
5. 执行 backend typecheck、默认 dry-run、`git diff --check` 和禁止改动路径检查。

非 live 测试只能证明结构、接线、边界与预算正确，不能证明语义召回改善。

### 8.2 Live 最小证伪实验

实现与非 live 验证完成后，必须再次取得用户对模型、最多请求数和费用上限的明确授权，才可执行：

- 固定两份 fixture。
- 每份最多一次 Selector-only 请求，总计最多 2 次。
- 模型继续使用 GLM-5.2。
- `thinking=disabled`、目标工具、`maxAttempts=1` 保持不变。
- 不运行 Builder、数据库、selection、fallback、repair、retry 或浏览器全链路。

第一轮成功口径：

- 两份结构均通过。
- 靖康、鸿门宴风险召回 `2/2`。
- 玄武门、巫蛊之祸 `none` 保持 `2/2`。
- candidate ID 精确覆盖、rank 完整、请求数不超过 2。

单次固定回放通过只说明方向获得初步支持，不足以声明长期稳定。若任一风险仍漏判或 `none` 对照误报，应判定当前 prompt 假设未通过，不在本任务中继续堆叠更多规则或示例。

## 9. 影响范围

预计实施只涉及：

- `harness/prompts/topic/selector.prompt.md`
- 对应 prompt 约束测试
- `harness/samples/topic-selector-semantic-replay/task17-balanced.fixture.json`
- fixture 说明、回放统计测试与当前基线记录
- 本设计对应的中文实施计划

如果实施过程中发现必须修改生产 DTO、parser、shared/API、前端或 downstream 合同，应停止并重新设计，不得借本任务扩张范围。

## 10. 风险与止损

1. **模型仍跳过内部审查**：由固定 live 回放直接否证，不继续追加提示词口号。
2. **风险召回提高但误报 `none`**：视为质量闸门未通过，不以 recall 单项改善宣称成功。
3. **prompt 膨胀**：通过改写现有判断顺序控制规模，不加入第一轮 few-shot 示例。
4. **评测范围被误解为降低标准**：党锢项不是改判为正常，而是从不匹配职责边界的自动硬指标移到人工观察；靖康与鸿门宴仍是严格门禁。
5. **本地语义规则渗入**：代码审查必须检查没有新增候选正文读取、关键词表、正则、评分或语义分支；一旦发现立即停止实施。
