# 计划状态治理收口设计

- 日期：2026-08-11
- 状态：设计已批准，等待实施
- 范围：`docs/plans/` 当前入口、历史计划归档与状态真相源校准

## 1. 背景与问题

`docs/plans/README.md` 已规定：根目录只保留准备执行、正在执行或刚完成等待收口的设计与实施计划；已经完成、被正式文档吸收或仅具历史追溯价值的文件应移入 `docs/plans/archive/`。

当前根目录除 `README.md` 外仍有 105 份计划文件。审计显示，它们分别属于以下三类：

1. 已经完成并有代码、测试、提交或状态文档佐证的计划。
2. 被后续实现、回滚或正式架构文档取代的旧草案。
3. 尚有未勾选步骤，但当前状态入口已明确要求如需重启必须新建当日设计与实施计划，不能继续执行的历史方案。

这些文件继续留在根目录会让新 agent 把历史步骤误判为当前任务，且已与 `AGENTS.md`、`docs/README.md` 和路线图的治理约定冲突。

## 2. 目标与非目标

### 2.1 目标

- 让 `docs/plans/` 根目录恢复为唯一、可信的当前计划入口。
- 保留全部历史计划内容和 Git 追溯，不重写历史实施证据。
- 校准 Asset Planning 最近两组计划的 live 证据边界。
- 让 `docs/plans/README.md` 与 `docs/todos/roadmap-todo.md` 表达同一套当前状态。

### 2.2 非目标

- 不修改业务代码、Prompt、schema、API、测试或生成态 storage。
- 不重新运行付费 provider 或 DashScope 小样本。
- 不把后续 `S2-2`、前端六步浏览器验收等新任务混入本次收口。
- 不修改现有未跟踪脚本。

## 3. 方案比较

### 方案 A：只更新状态入口

只修改 `docs/plans/README.md` 和路线图。改动最小，但 105 份旧文件仍会继续充当错误入口，不能解决根因。

### 方案 B：全量归档并校准真相源

把根目录全部 105 份历史计划移入 `docs/plans/archive/`，保留文件内容和文件名；同时更新状态入口与路线图。该方案不删除证据，也不重写历史内容，能一次消除入口污染。

### 方案 C：逐份重写历史状态

保留原位置并为每份文件补写最终状态。该方案工作量大，容易把后来的认识倒灌进历史证据，而且仍不能让根目录保持简洁。

采用方案 B。

## 4. 归档判定与目录边界

本次把 `docs/plans/README.md` 之外的现有 105 份文件统一视为历史证据并移入 `docs/plans/archive/`。归档前检查表明目标目录不存在同名文件冲突。

归档采用文件移动，不改写历史结论、复选框或实施记录。为了保留历史证据的可读性，只允许对 Markdown 相对链接做机械重定向：

- 归档文件之间的 `./2026-*` 同级链接保持不变。
- 从归档文件指向 `docs/records/`、`docs/architecture/`、`docs/todos/` 等目录的链接按新增目录层级重写。
- 从正式架构、harness、路线图和 records 指向原计划根目录的链接改指向 `docs/plans/archive/`。
- 归档完成后运行本地 Markdown 链接目标检查；本次移动不得新增指向不存在本地文件的链接。

当前状态、正式架构与执行规则继续由以下入口承担：

1. `AGENTS.md`
2. `docs/README.md`
3. `docs/architecture/`
4. `harness/README.md`
5. `docs/plans/README.md`
6. `docs/todos/roadmap-todo.md`

后续新任务需要设计与实施计划时，必须使用当日日期新建中文文档；任务完成后及时归档。

## 5. Asset Planning 证据校准

语义意图编译器的 15 分镜和 21 分镜 live 双闸门运行了包含既有 global normalization/repair 逻辑的当前代码版本。7 个有效 provider 轮次全部端到端成功，但全部停留在正常路径，因此只能证明当前 global 正常路径与意图编译主链路兼容。

但这 7 个有效轮次的 `global_structure_normalization_event_count` 均为 0，`global_structural_repair_used` 均为 `false`。因此结论必须保持精确：

- global 正常路径：已有 live 证据。
- global normalization 与 structural repair 异常恢复分支：已有完整 non-live 回归，未在后续 live 中实际触发。
- 不新增付费 live；剩余风险留在状态入口，未来只有在真实故障复现或单独授权时再验证。

这不阻止计划归档，因为显式 live 本来就不是默认自动化门，且当前默认 `intent_compiler` 迁移已经独立通过正式双闸门。

## 6. 状态入口调整

`docs/plans/README.md` 调整为简洁的当前入口：

- 明确根目录完成本轮清空，只保留 README 和未来真正的当前计划。
- 指向最近 Asset Planning live 记录与归档位置。
- 列出当前推荐顺序：先做前端 v1 六步真实浏览器验收矩阵，再评估 `S2-2`。
- 明确旧计划不得从 archive 继续执行。

`docs/README.md` 同步调整计划入口语义：

- 将 2026-07-13 V2 设计草案降级为历史输入，不再称为后续 V2 功能的当前审查入口。
- 明确 `S2-2` 等尚未启动的 V2 工作必须基于正式架构、当前代码与实际验证结果新建当日 design + implementation plan。
- 保留对 archive 的追溯入口，但不允许从历史草案直接续跑。

`docs/todos/roadmap-todo.md` 调整为：

- 将“收口当前未归档计划”标记完成。
- 保留“前端 v1 真实浏览器验收矩阵”为当前产品任务。
- 记录 global repair live 分支未触发为剩余风险，不把它升级为默认付费任务。

## 7. 验证与提交

本次验证必须包括：

1. 根目录只剩 `README.md` 和本次正在执行的治理文档；最终提交后治理文档也进入 archive。
2. 归档前后的计划文件总数一致，无丢失、无同名覆盖。
3. 当前入口不再链接根目录中的历史计划路径，也不再把 archive 草案称为当前执行入口。
4. 本地 Markdown 文件链接检查确认本次移动没有新增断链。
5. `git diff --check` 通过。
6. `git status --short` 只包含本任务文档移动与状态修改，以及用户原有的两个未跟踪脚本。

本任务按低耦合提交拆分：先提交设计，再提交实施计划，最后提交归档与状态校准。
