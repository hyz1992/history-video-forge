# story-video-forge2 Harness 工程规则与风险规避

## 1. 总原则

新项目采用 `greenfield-first`，不是 `refactor-first`，但同样必须坚持：

- 一次只做一个低耦合任务
- 先设计、再实现、再验证、再自审
- 所有阶段边界必须文档化
- 所有关键对象必须显式命名，不能只靠 prompt 隐式约定

## 2. 当前最重要的风险规避规则

### A. 避免 prompt 过重

- 不把规则分散在多个互相打架的 prompt 中
- 优先用结构化对象表达边界
- family/style/delivery 都必须是轻量配置，不是大段 prose prompt

### B. 避免前后阶段打架

- topic 阶段定义边界
- script 阶段不能偷偷重定义 topic
- storyboard 阶段不能偷偷重定义 script

### C. 避免无限重试

- 推荐阶段失败以淘汰坏候选为主
- script 阶段只允许有限 patch/regenerate
- 任何阶段不得默认无限自动重试

### D. 避免时长误用

- 时长只做后验范围检查
- 不允许轻微时长偏差直接打回正文

### E. 避免隐式状态丢失

- 必须维护仓库内 todo
- 已确认结论必须落正式文档
- 未确认项必须显式 `TBD`

## 3. 任务执行契约

每次开始执行前，必须写清：

- 任务
- 目标
- 改哪些文件
- 不改什么
- 验证方式

每次结束时，必须写清：

- 实际改动
- 验证结果
- 自审结论
- 剩余风险

## 4. 文档优先级

正式规范优先级：

1. `docs/requirements/*`
2. `docs/architecture/*`
3. `docs/data/*`
4. `docs/standards/*`
5. `docs/ui/*`
6. `docs/plans/*`
7. `docs/todos/*`

## 5. 最小验证原则

- 没有验证，不得声称完成
- 能做本地确定性检查的，不交给 LLM
- LLM 审校只能有一个主裁判
- prompt 输出格式必须结构化

## 6. Todo 规则

- 必须维护一个仓库内 todo 文件
- todo 里要显式区分：
  - 已完成
  - 进行中
  - 待做
  - 阻塞项

## 7. 当前文档化策略

- 已确认结论：写入正式文档
- 讨论中但未拍板：不要写成正式规范
- 过程性推导：可在路线图或 TODO 中记录，不写成强规则
