# story-video-forge2 原始需求文档

## 0. 这是什么项目

`story-video-forge2` 是一个**面向历史故事短视频的 AI 生成系统**。

它不是通用视频生成平台，也不是通用内容工厂。  
它的唯一产品焦点是：

- 从选题到口播脚本、再到后续分镜与素材阶段，稳定产出有爆款潜质的历史故事短视频。

它的核心挑战不是“能不能生成”，而是：

- 能否稳定生成
- 能否减少失败重试
- 能否避免 prompt 前后打架
- 能否在保证历史边界的同时做出短视频抓力

## 1. 项目背景

旧项目 `story-video-forge` 经过多轮修改后，虽然主流程可运行，但出现了以下问题：

- `script` 阶段过重，存在多层合同、多轮重写、多头裁判
- prompt 负担过重，前后环节容易打架
- 大纲审核失败、语义审校失败等问题频发
- 时长经常被误用为正文质量 gate
- 文案、分镜、素材阶段都在重复理解故事
- 产出质量不稳定，爆款短视频潜力不够强

因此需要在新的空目录中，以更精简、更稳定、更可验证的方式重新开发。

## 2. 项目目标

新项目唯一产品焦点：

- 稳定产出有爆款潜质的历史故事短视频

核心目标：

- 新建一个干净项目，而不是继续给旧项目补丁
- 继承旧项目成熟基础设施，而不继承旧内容链路
- 构建更科学的主题阶段与 script 阶段
- 控制 prompt 重量与跨阶段打架风险
- 提升产出稳定性、审核通过率和工程可维护性

## 3. 产品核心定义

新项目的产品本质可以概括成一句话：

> 通过结构化上游边界、轻量候选筛选与有限修补，把“历史故事短视频”的生成过程做成稳定、可复验、可扩展的流水线。

这里的“稳定”包括：

- 同一个题材不会每次写成不同东西
- 不会因为轻微格式或时长偏差进入重试风暴
- 主题、脚本、分镜阶段不会反复重讲同一个故事
- 后续 agent 在没有上下文时仍能读文档接手

## 4. 用户与主要使用场景

当前主要假设用户为：

- 需要批量或持续生产历史短视频的人
- 希望系统在“系统推荐 / 事件库 / 自定义输入”三种入口下都能稳定工作
- 更关注结果稳定性和效率，而不是无限手工调 prompt

核心使用场景：

1. 用户新建一个任务，系统推荐 3-5 个值得讲的历史题
2. 用户从事件库中主动指定一个历史事件，再从系统生成的 candidate 中确认一个讲法
3. 用户输入一个成语、事件名或故事简介，系统识别后生成 candidate，再确认进入 script

## 5. 新项目的核心流水线

当前已确认的上游到中游主链路：

```text
系统自动推荐 / 事件库 / 自定义输入
-> 事件识别或开放发现
-> Event Registry 归一化
-> Topic Candidate Builder
-> Topic Candidate Card
-> 用户确认
-> Topic Package
-> Topic Delivery Pack
-> Script Input Bundle
-> Script Draft Package
-> 本地硬校验
-> 单一语义审校
-> 确认 script
```

说明：

- `Topic Candidate Card` 是给用户看的候选对象
- `Topic Package` 是 script 阶段唯一正式上游输入
- `Topic Delivery Pack` 是单题交付微调包
- `Script Input Bundle` 是 script 阶段真正消费的统一输入对象

后续阶段如 storyboard / assets / compose 仍需继续设计，目前为 `TBD`。

## 5.1 明确复用范围

允许复用：

- LLM 调用与结构化输出修复能力
- 生图/生视频/语音/合成基础设施
- 前后端技术栈
- 现有 UI 风格能力与布局能力
- trace / diagnostics / runtime harness 经验

不直接复用：

- 旧项目内容链路与状态机
- `StoryBrief / ScriptBrief / OutlinePlan` 三层主合同
- 旧的系统推荐选题流程
- 旧的自定义主题 draft 编辑方式

## 6. 关键设计原则

1. 只在必要处使用 LLM，能本地做确定性检查的优先本地化。
2. 每个阶段只回答一个问题，不允许跨阶段重讲故事。
3. 主题阶段输出的是 `Topic Package`，不是自由 prose。
4. script 阶段默认单稿，不重新做大规模候选选稿。
5. 时长只做后验范围匹配，不是先验精确秒数 gate。
6. 风格层采用“项目固定 + family 偏置 + 单题微调”，不走全写死或全实时。

## 7. 成功标准

### 第一阶段成功标准

- 主题阶段从三入口到 `Topic Package` 稳定闭环
- `Topic -> Script` 的输入边界清晰且轻量
- script 阶段默认单稿、有限修补，不再重型重试
- 可通过文档直接指导 greenfield 开发

### 第二阶段成功标准

- 主题阶段与 script 阶段能稳定跑通真实样例
- 明显降低格式失败、范围漂移、重试风暴
- 产出的口播与包装具备更强的短视频抓力

## 8. 非目标

当前不追求：

- 兼容旧项目全部历史状态与数据结构
- 继续维护旧主题库驱动的主题选择逻辑
- 一次性完成全链路所有阶段的实现细则
- 在没有确认规则前就开始实现大量功能

## 9. 当前已确认的产品方向

- 主题页面使用 3 个 tab：
  - `系统自动推荐`
  - `事件库`
  - `自定义主题`
- 三条入口最终统一收敛到：
  - `Topic Candidate Card`
  - 用户确认
  - `Topic Package`
- `Topic Package` 是 script 阶段唯一正式上游输入
- 时长是后验范围匹配，不是先验硬 gate

## 10. 当前重大风险

- 推荐入口回流到明星题与重复题
- family 不够覆盖，导致不同题材被讲得别扭
- `Topic Package` 重新变重，长成新的 narrative brief
- script 阶段再次膨胀为多稿、多审、多轮重试
- 风格系统重新变成 prompt 杂糅层
