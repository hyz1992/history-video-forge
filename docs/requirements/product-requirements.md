# story-video-forge2 原始需求文档

## 1. 项目背景

旧项目 `story-video-forge` 经过多轮修改后，虽然主流程可运行，但出现了以下问题：

- `script` 阶段过重，存在多层合同、多轮重写、多头裁判
- prompt 负担过重，前后环节容易打架
- 大纲审核失败、语义审校失败等问题频发
- 时长经常被误用为正文质量 gate
- 文案、分镜、素材阶段都在重复理解故事
- 产出质量不稳定，爆款短视频潜力不够强

因此需要在新的空目录中，以更精简、更稳定、更可验证的方式重新开发。

## 2. 项目目标

新项目唯一产品焦点：

- 稳定产出有爆款潜质的历史故事短视频

核心目标：

- 新建一个干净项目，而不是继续给旧项目补丁
- 继承旧项目成熟基础设施，而不继承旧内容链路
- 构建更科学的主题阶段与 script 阶段
- 控制 prompt 重量与跨阶段打架风险
- 提升产出稳定性、审核通过率和工程可维护性

## 3. 明确复用范围

允许复用：

- LLM 调用与结构化输出修复能力
- 生图/生视频/语音/合成基础设施
- 前后端技术栈
- 现有 UI 风格能力与布局能力
- trace / diagnostics / runtime harness 经验

不直接复用：

- 旧项目内容链路与状态机
- `StoryBrief / ScriptBrief / OutlinePlan` 三层主合同
- 旧的系统推荐选题流程
- 旧的自定义主题 draft 编辑方式

## 4. 成功标准

第一阶段成功标准：

- 主题阶段从三入口到 `Topic Package` 稳定闭环
- `Topic -> Script` 的输入边界清晰且轻量
- script 阶段默认单稿、有限修补，不再重型重试
- 可通过文档直接指导 greenfield 开发

第二阶段成功标准：

- 主题阶段与 script 阶段能稳定跑通真实样例
- 明显降低格式失败、范围漂移、重试风暴
- 产出的口播与包装具备更强的短视频抓力

## 5. 非目标

当前不追求：

- 兼容旧项目全部历史状态与数据结构
- 继续维护旧主题库驱动的主题选择逻辑
- 一次性完成全链路所有阶段的实现细则
- 在没有确认规则前就开始实现大量功能

## 6. 当前已确认的产品方向

- 主题页面使用 3 个 tab：
  - `系统自动推荐`
  - `事件库`
  - `自定义主题`
- 三条入口最终统一收敛到：
  - `Topic Candidate Card`
  - 用户确认
  - `Topic Package`
- `Topic Package` 是 script 阶段唯一正式上游输入
- 时长是后验范围匹配，不是先验硬 gate
