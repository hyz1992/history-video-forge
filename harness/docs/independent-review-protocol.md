# 独立审查协议（Independent Review Protocol）

适用项目：`history-video-forge`

本文定义会话内"实施 → 独立审查 → 整改 → 复审"循环的执行规范。
目标是把外部审查循环（实施者提交 → 人工转交外部 reviewer → 人工转回意见）内化为 agent 会话内的低摩擦循环，同时保留用户终审闸门。

---

## 定位与边界

- 审查子代理的独立性来自**全新上下文 + 最小 review package**，不继承实施者的实现视角。
- 审查子代理是**只读**的：不得修改工作树、不得修改迁移与运行状态、不得提交。
- 本协议不替代以下事项，原有规则继续生效：
  - 真实运行时验证（浏览器验收、live provider、Remotion 导出）仍按 `AGENTS.md` 与 `harness/README.md` 显式执行并记录证据；
  - 语义质量判断（script 首稿"可用线 / 爆款首稿线 / 发布线"等）不属于本地审查能力；
  - 用户终审：关键任务收敛后仍由用户做最终闸门复审。
- 审查子代理与主 agent 使用同一模型；独立性是上下文性的，不是跨模型对抗。该局限由用户终审与里程碑校准审计对冲（见下文）。

## 审查分级

任务开始的结构化输出必须声明**审查级别**。判定直觉：**"这个改动如果错了，最坏炸什么？"**——炸的是"一个颜色显示不对"归 T0，炸的是"manifest 合同、事务原子性、provider 费用"归 T2。

| 级别 | 判定信号（满足其一即归入） | 审查要求 |
|---|---|---|
| T0 微小改动 | 纯视觉参数（颜色/边距/间距）、文案、注释、计划文档勾选，不改任何逻辑分支 | 不启动审查子代理；跑对应最小检查（多数情况无需跑测试）；常规自审后提交 |
| T1 局部逻辑 | 模块内逻辑改动，不碰 shared schema / API / prompt / 跨阶段合同 | 一轮 diff_reviewer；无 Critical 即收敛 |
| T2 高风险 | shared schema、API、prompt、validator、状态机、事务/并发、费用相关、跨阶段合同 | diff_reviewer + contract_reviewer 收敛后，final_reviewer 按 R5 两阶段流程终审（每个候选收敛周期一次，见收敛条件） |

分级规则：

1. **只升不降**：实施中实际触碰文件超出任务开始声明范围、或发现牵连合同/状态机/事务时，必须当场升级重分类并重新声明，不允许"改着改着变大了仍按低级别走"。升级为 T2、或 T1 任务实际触碰适用 R1 的状态型功能时，回溯冻结 TASK_BASE_SHA 至任务首个改动前的 HEAD，升级前改动纳入累计 diff。
2. **用户覆盖**：用户点名"按 T2 审"是硬指令，不受分级影响。
3. **分级可追溯**：级别声明与实际 diff 可事后核对；把 T2 任务标成 T0 视为审查缺失，终审时按此追责。

## 审查者角色

三个角色。主 agent spawn 子代理时，必须把对应角色的完整指令放进 prompt，不得只写角色名。

### diff_reviewer

只读审查普通任务 diff，关注正确性、行为回归、测试缺口与范围越界。

- 以独立代码所有者视角审查提供的计划片段、diff 与验证结果。
- 优先级顺序：正确性、行为保真、缺失测试（尤其失败路径对抗测试）、集成回归、超出任务范围的改动。
- 检查依据为 `review-checklist.md`，重点是其中的高频问题专项清单。
- 输出必须给出具体 finding 与精确文件引用；未发现问题时显式声明"未发现"，并列出残余证据缺口。
- 只依据最小 review package 判断；缺少必要材料时明确说缺什么，不凭无关历史推断。

### contract_reviewer

只读审查设计合同一致性，对应 `self-review-methodology.md` 视角 1（合约对照）。

- 打开设计文档/实施计划，提取显式约束（字段名、枚举值、状态名、API 路径、错误码、计划勾选项），逐字段 diff 实现。
- 核对 `docs/`、`shared/src`、`harness/` 三处是否表达同一套约束，是否出现双真相源或约束漂移。
- 用源码验证，不用记忆；发现"差不多"的实现即报 finding。
- 文档承诺与代码行为不一致时，以用户原始要求为基准报偏差，不自行裁决改哪边。

### final_reviewer

只读终审，只能在适用的专项 reviewer finding 全部收敛后调用；**每个候选收敛周期至多一次**（终审发现 Critical/Important 时该候选失败，重开收敛形成新候选后可再次终审，见收敛条件）。

- 从用户原始请求/验收清单提取验收范围（不得只沿用提交说明、实施者总结或 PR 描述）。
- 逐项标注 `已修`、`部分修`、`未修`、`未验证`，并说明证据来源（代码位置、测试命令输出、浏览器实测或接口输出）。
- 区分"实现者声称已修"与"用户原始要求"的范围；两者不一致时以后者为准。
- 不得把缺失证据当 PASS；环境无法验证的项必须标 `未验证`。
- 不重做广泛探索，除非点名了具体证据缺口。

## 最小 review package

主 agent 只向审查子代理提供以下内容，不提供完整会话 transcript、无关历史或全部旧模块文档：

1. 目标与允许范围（任务开始的结构化输出：任务 / 目标 / 改动文件 / 不改什么 / 验证方式 / 审查级别）
2. 相关设计文档或实施计划的精确片段，或路径 + 章节定位
3. 实际 diff：T2（及适用 R1 的 T1）任务为 `TASK_BASE_SHA..HEAD` 累计 diff + 当前未提交改动（必须），上轮增量 diff 仅作辅助；其他任务为 `git diff` 输出或改动文件清单与关键内容
4. 验证命令与结果
5. 复审时：未闭合 finding 清单与上轮修复说明
6. 待回答问题（可选）

> **final_reviewer 特化（R5）**：上述第 5 项与实施者整改叙事只提供给 diff_reviewer / contract_reviewer 的复审轮；final_reviewer 的输入按 R5 去叙事化执行（只含原始需求、设计/计划定位、base/head SHA、代码与 diff），独立形成 finding 后再提供第 4 项验证证据核对。

## finding 输出格式

- 分级：`Critical`（正确性或合同违反，必须修）、`Important`（应修，不修需书面说明理由）、`Minor`（可选改进）。
- 每条 finding 必须附证据位置：`文件:行号`、命令输出或文档章节。
- 无 finding 时必须显式输出"未发现"，并列出残余证据缺口；不得把"没看到问题"表述为"通过"。

## 收敛条件

- T1：一轮 diff_reviewer 无 Critical 即收敛。
- T2：diff_reviewer 与 contract_reviewer 均无 Critical 且 Important 全部闭环后，final_reviewer 对该候选终审一次（按 R5 去叙事化输入）。
- **终审闭环路径**：final_reviewer 发现 Critical 或 Important 时，该候选收敛周期失败；修复后必须**重新经过 diff_reviewer + contract_reviewer 收敛**，形成新候选后再调用一次 final_reviewer。"调用一次"限定为**每个候选收敛周期一次**，不是整个任务生命周期一次；同一任务的多个候选周期可以有多次 final（每次都是对新候选的独立终审，前一次终审已判该候选失败，不存在"同一候选重复终审"）。final 只发现 Minor 时不重开，Minor 随候选收尾处理或留档。
- **循环上限**：同一任务内审查-整改循环不超过 3 轮；**每轮 = 一次"整改 + 复审"迭代**，任务初始 diff/contract 审查不计轮，轮从首次整改后的复审起算；同一候选周期内 final 至多一次（见终审闭环路径），3 轮上限覆盖所有候选周期的全部迭代；final 终审本身不单独计轮，其失败后触发的整改+复审计入轮数。候选形成阶段（重开收敛）的 diff/contract 反复不收敛同样消耗轮数，不允许无限重试（对齐 `AGENTS.md` 禁止事项）；**用户明确授权的例外除外**——协议要求达到上限后停止并向用户报告，用户明确批准的一次受限例外是合理的人工闸门，不属于自主重试。
- **术语**：**候选** = 通过 diff_reviewer + contract_reviewer 收敛、等待终审的代码状态；**候选收敛周期** = 从候选形成到终审判定（通过或失败）的完整过程。

## T2 审查硬约束（R1-R6）

本节由 S2-2A 任务 7 四轮外部校准审计的重复 finding 沉淀而来。溯源映射（外部审计轮次 → 沉淀规则，供「校准与终审」节对照漏检率）：

| 外部审计轮次 | finding 类别 | 沉淀规则 |
|---|---|---|
| 二轮 P1-A / 三轮 I-1 | 组合缺陷（两个正确修复组合出新状态） | R1 + R2 |
| 三轮 I-2 / 四轮 I-1 | 安全边界半校验（hostname 精确但漏协议/端口/空串） | R4 |
| 二轮 P3-A | 错误来源假阳性（this 解绑冒充事务失败） | R4 |
| 一轮 P1-3 | 名义类型 vs 不可信运行时数据（15.5 → BigInt） | R4 |
| 二轮 P1-1 / 一轮 P1-1 | 模块级正确误当链路级正确（接线缺位） | R1 + R3 |
| 三轮 Minor | 记录计数失真（凭印象填 8 实际 7） | R6 |
| 二轮 P1-1（终审叙事锚定） | final_reviewer 输入含整改叙事 | R5 |

**T2 任务（shared schema / API / prompt / validator / 状态机 / 事务并发 / 费用 / 跨阶段合同）必须逐条执行**；T1 任务按相关性适用——满足以下任一触发条件即适用对应条款：触碰状态型功能（R1/R3）、触碰安全边界或不可信外部输入（R4）、产生新分支/新状态（R1/R2）、记录中填写任何测试数字（R6）、执行终审（R5）。六条硬约束：

**R1 整改后增量全审**：每轮整改完成后，**从任务固定基准到当前 HEAD 的完整累计 diff** 必须作为独立审查对象重新审查一次，不得只复查上一轮 finding 清单，也不得只审查本轮整改补丁。任务开始时主 agent 必须冻结 `TASK_BASE_SHA`（任务首个改动前的 HEAD），并**记录初始工作区状态与任务文件范围**：不得自行提交、stash 或移动无关的未提交改动（可能属于用户）；同文件存在无法安全区分的重叠改动时，停止并请求用户处理；累计 diff 只包含任务授权范围；每轮审查向 reviewer 提供：`TASK_BASE_SHA..HEAD` 累计 diff + 当前未提交改动（必须），上轮 review head → 当前 head 的增量 diff 只能作为辅助（可选）。只传最新整改补丁会让 reviewer 看不到"旧实现 × 新修复"的组合缺陷。为修复 finding 新增的分支、状态和数据维度一律视作新功能。

**R2 finding 不变量化**：每个被接受的 Critical/Important finding（以及揭示某一类问题的 Minor）必须提炼成一条**不变量**（描述性命题，不含具体反例）并闭环验证。闭环方式按 finding 类型分流：
- 行为型/状态型 finding（逻辑分支、状态机、事务、边界输入）：基于不变量生成**至少两个反向组合自动化测试**；
- 文档/流程型 finding（合同漂移、记录计数、过程违规）：机器检查（grep/脚本断言等）或**两项独立验证**（如两次独立来源核对）；计数类 finding 的替代证据必须包含对实际运行输出的核对（与 R6 一致），不得两次静态核对同一陈旧来源；
- live/UI 型 finding（浏览器、真实 provider）：真实运行证据；
- 不适用自动化测试的 finding：记录不适用理由与替代证据，由 reviewer 确认替代证据成立后闭环。
反例只证明"这个例子修好了"，不变量测试才证明"这一类问题不存在"。纯外观/措辞级 Minor 不强制。示例：
- 反例："disabled 项不能派发" → 不变量："只要存在 capability/provider/model/scope 完全匹配的 active 行，其他旧行的状态与遍历顺序不得影响结果" → 测试：disabled 在前 active 在后、active 在前 disabled 在后、多错误 scope、Map/hydrate 顺序反排。
- 反例："hostname 不能带恶意后缀" → 不变量："只有明确允许的 HTTPS origin（scheme + hostname + port）才能获得已知区域、报价与派发许可" → 测试：http/ftp/非 443 端口/私有域名/无法解析全部 fail-closed。

**R3 生命周期序列测试**：状态型功能（目录、迁移、状态机、事务、配置）不允许只用全新 `createDbClient()`/fresh state 测试。必须覆盖状态迁移序列，至少选择 4 类：
- `upgraded`：旧版本数据 → 新版本代码启动（旧行被禁用、新行被追加、两行共存）；
  选择时必须包含与本次改动状态流转直接相关的类别（如迁移改动必须含 `upgraded`、区域/配置切换必须含 `switched`、批量写入必须含 `partially_failed`），不允许只挑最容易构造的 4 类；
- `switched`：区域/配置切换（北京 → 新加坡 → 北京，旧行保留 disabled）；
- `recovered`：失败前缀 → 重启恢复（事务半应用后重跑）；
- `duplicated`：历史重复行/同 model 多行共存；
- `reordered`：Map/hydrate 顺序变化；
- `partially_failed`：批量写入中段失败。
外部审查按"数据库内容可以损坏、部署历史可以遗留"构造状态；序列测试是本地复现该姿势的唯一途径。

**R4 完整对象验证**：安全边界与错误路径按完整对象验证，不验证局部形状。
- URL/endpoint 类校验必须覆盖全部要素：scheme、hostname、port（必要时 path/origin）；缺失任一要素的绕过路径必须 fail-closed。
- 数据库/外部错误必须断言**来源与类型**（如 CHECK 约束错误而非 `this` 解绑 TypeError），并证明测试真正经过了目标代码路径（如"事务执行到第一条成功写入之后才失败"）；只断言"发生了异常 + 数据没留下"是假阳性温床。
- 类型系统不保证运行时内容：来自数据库 JSON、env、文件的外部输入一律按不可信数据设计测试（`15.5`、超安全整数、`NaN`、空字符串、非法协议）。

**R5 终审去叙事化**：final_reviewer 的输入只包含：用户原始需求/验收清单、设计文档与实施计划定位、base SHA、head SHA、代码与 diff、当前未提交改动。**不得包含**实施者的整改说明、处置理由、"我们修了什么"或"哪些测试已通过"。终审独立形成 finding 后，再提供测试证据供其核对。实施者叙事（含上轮 finding 清单）是锚定源，会显著降低终审独立性；diff_reviewer 的复审轮可携带未闭合 finding 清单（这是 diff 层职责），但 final_reviewer 始终按 R5 执行。

**R6 证据纪律**：审查记录与验收表中的测试数量、命令输出、状态标注必须**从实际运行结果重填**，禁止凭印象填写（历史教训：记录写"8 个测试"实际 7 个）。每轮审查记录落盘前，主 agent 必须对照最后一次运行输出核对全部数字；reviewer 发现记录与实测不符时按 Important 报 finding。

执行方式：R1-R5 由主 agent 在 T2 任务的每轮整改与审查编排中落实；R6 对全部任务生效。

## 会话内执行方式

- 使用 Agent 工具 spawn 审查子代理，类型用 `general-purpose`，并在 prompt 中写明只读约束：只允许读取文件与运行验证命令（测试、类型检查、`git diff`/`git log` 等只读 git 子命令），禁止编辑、写入、暂存、提交。
- 只读约束的落点验证：每轮审查结束后，主 agent 运行 `git status --porcelain` 核对工作树与审查前一致；发现子代理改动即视为违规，回滚并重跑该轮。
- **禁止递归 fan-out**：审查子代理不得再 spawn 审查子代理。
- 报告中不得声称"跨模型审查"或"独立模型复核"；如实描述为"同模型、新上下文独立审查"。
- 每轮审查前，主 agent 执行 `git diff --name-only TASK_BASE_SHA..HEAD`（T2 及适用 R1 的 T1）并与任务声明的改动文件清单比对，确认累计 diff 只包含任务授权范围；发现范围外文件（含任务期间 dev 分支外部提交混入）立即停止并向用户报告。
- **final_reviewer 两阶段交接机制（R5 执行方式）**：阶段一，主 agent spawn final_reviewer，输入只含用户原始需求/验收清单、设计文档与实施计划定位、`TASK_BASE_SHA`、当前 HEAD、累计 diff 与未提交改动；阶段二，final_reviewer 返回独立 finding 后，主 agent 用续问（SendMessage）向**同一 final 子代理**补充验证命令与结果，由其核对证据并给出终审结论。两次消息属于同一次终审（同一候选周期一次），不是两次 spawn 终审；禁止在阶段一输入中夹带验证结果、未闭合 finding 或整改叙事。

## 证据与落盘

- 任务完成的结构化输出必须包含：审查级别、审查轮次、各轮 finding 数（Critical / Important / Minor）、修复证据（文件位置或测试命令输出）。
- T2 任务的审查记录（finding 与闭环证据）写入 `docs/records/` 对应记录文件，格式从简：结论、有效 finding、修复结果。
- 不保存平台调用回执、模型信息或 token 数据；它们不属于产品正确性证据。

## 校准与终审

- **用户终审保留**：T2 任务收敛后仍需用户做最终闸门复审；本协议把"每轮外审"降为"每个候选收敛周期终审一次"（见收敛条件），不是取消终审。
- **里程碑校准审计**：每个大里程碑（如一个 S 阶段收尾）由用户安排一次外部审查（如 codex），对照内部循环是否漏掉其发现的问题。漏得少则可继续放宽内化程度；漏得多则提高终审频率。内化程度由证据决定，不一次拍板。

## 反递归边界（harness 自身维护）

- 本协议**不审自己的首次落地**；首次落地由用户终审把关。
- 之后的协议修订按 T1 分级走正常审查流程。
- 将来如新增 task-gate 类硬门禁脚本：必须在干净会话（不夹带产品任务上下文）中实施，用隔离 fixture 与单测验证，先 shadow-only（只输出建议、不阻断），稳定后才考虑强制；不得要求待修改的验证器先验证自己的替代品。
- harness 维护任务不进入产品阶段闸门序列，不触发产品链路的最小验证回跑。
