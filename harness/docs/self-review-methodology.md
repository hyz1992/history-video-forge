# 自审方法论（Self-Review Methodology）

适用项目：`history-video-forge`

本文是对 `definition-of-done.md` 第 6 条"自审完成"的具体操作规范。
源于 publish 阶段实现中多轮自审仍漏掉 7 个问题的复盘。

---

## 核心原则

自审不是"再读一遍代码"。自审是用**不同的视角**重新审视同一套代码。
如果只用实现时的视角重读，什么也发现不了。

---

## 自审的六个视角

每次自审必须按以下顺序完成六个视角的检查。每个视角独立进行，不交叉。

### 视角 1：合约对照（Contract Audit）

**目标**：验证实现是否正确履行了设计合同。

**操作**：
1. 打开设计文档，提取所有显式约束（字段名、枚举值、状态名、API 路径、错误码）。
2. 打开实现的 schema / type / controller / 组件，逐字段 diff。
3. 用源码验证，不用记忆。

**参考案例**：
- `coverOriginLabel` 写的是 `ai_generated`，Zod schema 是 `generated`。如果打开 `publish-package.schema.ts` 看一眼，10 秒发现。
- `CoverArtifactSummary` 前端定义了后端不返回的字段。如果做了四层对照（Zod → 后端 snapshot → 前端类型 → 前端 template），秒发现。

**通过标准**：设计文档中的每个约束都能在代码中找到精确对应，没有"差不多"的实现。

### 视角 2：前后端交叉（Cross-Cut Audit）

**目标**：验证前端每个交互元素的真实状态是否与后端能力一致。

**操作**：
1. 列出所有 API 端点及其当前实现状态（注意区别"已实现 / stub / 501"）。
2. 列出前端每个按钮、输入框、链接。
3. 遍历每个前端元素，问："这个操作触发时，后端实际返回什么？"

**参考案例**：
- AI 生成封面按钮可点击，后端返回 501。分别审 controller 和 PublishPanel 时都没问题，但交叉看就暴露了。
- 封面 `file_uri` 作为 `<img src>`，但浏览器不加载 `file://`。单独看前端代码没问题，放到运行时上下文中就爆了。

**通过标准**：每个可交互元素的后端路径都已追踪到真实返回，前端状态正确反映后端能力。

### 视角 3：运行时模拟（Runtime Simulation）

**目标**：在脑中模拟"浏览器 → HTTP → 后端 → 返回 → 前端渲染"的完整链路。

**操作**：
1. 选一个用户操作（例如"上传封面"）。
2. 模拟：浏览器发什么请求 → 后端哪个 controller 处理 → 读哪些 DB 记录 → 返回什么 JSON → 前端哪个 computed 接收 → 渲染什么 DOM。
3. 标记每一步中可能失败的点（null check、网络错误、格式不匹配）。

**参考案例**：
- 封面 `file_uri` 在**浏览器**里是 `file://` 无法加载。代码作为文本是对的（有值、有 `:src`），但作为系统是错的（浏览器安全策略阻止）。
- 视频预览 URL `/api/projects/:id/render/preview` — 这个 endpoint 存在吗？返回什么 Content-Type？如果不走一遍运行时模拟，只是看到 computed 里有 URL 就觉得 OK 了。

**通过标准**：至少 3 个核心用户操作已完整模拟到 DOM 级别，无断链。

### 视角 4：循环打破（Normalization Break）

**目标**：识别因反复看到同一问题而产生的"正常化偏差"。

**操作**：
1. 列出所有当前 disabled / TODO / 待实现 / stub 的元素。
2. 对每个元素问："如果我是用户，这个状态会让我困惑吗？"
3. 对每个"待后续"标记问："后续是什么时候？为什么不是现在？"

**参考案例**：
- "导出发布包（待实现）"按钮看了四轮都没觉得有问题。发布交付包阶段的交付物是什么？没有导出，用户拿到什么？
- 2 个 snapshot 测试失败看了四轮，每次都写"预存在失败，与本次无关"。不是自己引入的 bug 不等于不该修。

**通过标准**：每个 disabled / TODO / stub 元素都有明确原因，且原因经得起"用户视角"检查。

### 视角 5：边界递减（Boundary Check）

**目标**：验证代码在异常路径下的行为。

**操作**：
1. 每个 controller：上游 record 不存在时返回什么？（不只是 null check，是实际返回码）
2. 每个 service：输入为空字符串 / null / undefined 时合理吗？
3. 每个前端组件：数据还没加载 / 加载失败 / 数据为空时分别渲染什么？
4. 每个测试：是否只有 happy path？错误路径有没有覆盖？

**参考案例**：
- 快照里 `coverPromptOptimizeController` 的 fallback — 如果 `currentPrompt` 为空字符串，返回 `optimized_prompt: ""`，前端 PATCH 过去会清空提示词。这是个边界 bug。
- `coverUploadController` 中 `manifestRecord` 为 null 时静默创建孤立 artifact — 原因是只测了 happy path。

**通过标准**：每个关键路径的 null/empty/error 三个状态都有明确行为且经过测试。

### 视角 6：视觉状态（Visual State Audit）

**目标**：验证 UI 的每一个视觉状态都正确。

**操作**：
1. 列出组件的所有渲染分支（loading / error / empty / normal / stale / blocked / ready 等）。
2. 逐一检查每个分支的视觉元素（图标、颜色、文案、按钮状态）。
3. 特别注意"部分完成"状态 — 不是"完全没做"也不是"全部完成"。

**参考案例**：
- 侧边栏 publish 步骤可以导航进入，但永远不会显示 ✓。实现者只验证了"能不能点"，没验证"完成态对不对"。
- 设计文档明确写了"侧边栏完成态由 `active_publish_package.readiness` 驱动"，但没有作为自审检查项。

**通过标准**：组件的每个渲染分支都已被列出，每个分支的视觉元素都被检查过。

---

## 自审流程

```
实现完成
    │
    ├─ 视角 1：合约对照（5-10 分钟）
    │   └─ 设计文档逐字段 diff
    │
    ├─ 视角 2：前后端交叉（5-10 分钟）
    │   └─ 端点列表 × 前端元素交叉矩阵
    │
    ├─ 视角 3：运行时模拟（5-10 分钟）
    │   └─ ≥3 个核心操作完整链路追踪
    │
    ├─ 视角 4：循环打破（3-5 分钟）
    │   └─ disabled/TODO/stub 清单 + 用户视角检验
    │
    ├─ 视角 5：边界递减（5-10 分钟）
    │   └─ null/empty/error 三态覆盖
    │
    ├─ 视角 6：视觉状态（3-5 分钟）
    │   └─ 渲染分支矩阵
    │
    └─ 输出自审结论（问题清单 + 修复后重新验证）
```

## 自审输出格式

```
自审结论：
- 合约对照：[通过/n 项问题]
- 前后端交叉：[通过/n 项问题]
- 运行时模拟：[通过/n 项问题]
- 循环打破：[通过/n 项问题]
- 边界递减：[通过/n 项问题]
- 视觉状态：[通过/n 项问题]

剩余风险：
- [尚未修复的问题]
```
